### 二次复核已确认结论（2026-09-11）

以下结论已经逐项确认，后续实现不得重新解释：

1. `休闲食品/糕点/点心/蛋黄酥` 按四个独立层级处理。四级独立保存不参与聚水潭成本价关联，成本价仍按 `douyin_sku_mappings.jushuitan_sku_id → products.sku_id` 关联；服务费匹配可以使用这四级路径，并由官方 `休闲食品////` 父级规则覆盖。
2. 抖店页面读取到的类目只作为本次查询的临时匹配上下文，不自动回写商品映射数据库。数据库中的导出类目仍需保持可追溯，页面类目不能静默覆盖原始导入数据。
3. 运费绑定页保留“店铺”下拉框，但只用于筛选和数据隔离；实际绑定对象仍是“店铺 + 商品ID”，不是店铺默认模板。
4. 扩展左下角“成本服务”只表示本机服务连接状态。商品缺重量、类目、运费或费率时，在商品卡片分别显示“未找到/未配置”，不能把单个商品数据缺失升级为全局“成本服务不可用”。
5. 基础服务费页面必须先可操作，费率目录先显示，商品覆盖数等慢统计异步加载；不能让整页长期被读取任务锁住。
6. 旧的无经营大类费率采用可恢复归档：从有效目录和匹配范围移除，保留历史、事件、备份和恢复入口，不做不可恢复的物理删除。
7. 同一类目不同生效日期的费率记录保留历史版本；当前日期只使用最新适用版本，页面明确区分“当前版本”和“历史版本”。新版本保存不覆盖旧记录。
8. 运费绑定商品区默认显示未绑定商品，同时保留全部/已绑定切换和商品名称、商品ID搜索。
9. 无法解析重量时按绑定模板首重/首费估算。通用模板按 1 kg / 3 元计算，界面必须标注“按首重估算”，但不能把 1 kg 写回商品实际重量。

## 2026-09-10 测试发现问题 1：修改经营大类时报唯一约束错误

### 问题现象与证据

- 在“基础服务费”页面选中“未配置经营大类”的旧规则，将经营大类改为“生鲜”后保存，页面弹出数据库原始错误：

  `UNIQUE constraint failed: basic_service_fee_rates.category_level_1, basic_service_fee_rates.category_level_2, basic_service_fee_rates.category_level_3, basic_service_fee_rates.category_level_4, basic_service_fee_rates.effective_from`

- 截图中旧规则的四级类目为“冷冻/冷藏制品 > 面点 > 中式面点 > 圆子/芋圆”，生效日期为 `2026-07-15`，原记录属于“未配置经营大类”。表单改成“生鲜”后，系统按当前页面规则尝试新增版本；错误发生在备份后写入阶段，而不是表单校验阶段。
- 页面提示写明“载入旧版本后保存，会以表单中的新生效日期创建新版本；原记录不修改”。因此当前操作的设计语义是“保留旧记录并创建新版本”，不是直接更新原记录。
- 问题截图：`C:\Users\23590\AppData\Local\Temp\codex-clipboard-c9f59aa1-e6d7-4e8c-a0ca-eb16dcb48c68.png`。

### 根因确认

1. 新代码的目标唯一键是“经营大类 + 四级类目 + 生效日期”。`cost_sync/database.py` 的新建表结构和 `cost_sync/service_fee.py` 的重复检查都包含 `major_category`。
2. 兼容迁移函数 `_ensure_service_fee_columns()` 只对旧表执行 `ALTER TABLE ... ADD COLUMN major_category`，并创建查询索引；SQLite 的 `ALTER TABLE ADD COLUMN` 不会重建旧表，也不会改变旧表已有的自动唯一索引。
3. 旧数据库的自动唯一索引仍是截图中显示的五列：四级类目 + 生效日期，没有 `major_category`。旧记录的经营大类通过新增字段补成空字符串，表单输入“生鲜”后，应用层按新六列键预检查不到重复，但数据库按旧五列索引拒绝 INSERT，于是把原始 `sqlite3.IntegrityError` 直接显示给用户。
4. 只读核对发现项目验收库 `storage/test/cost_accounting.sqlite3` 当前自动唯一索引已经包含 `major_category`。安装目录另有 `C:\Users\23590\AppData\Local\CostAssistant\data\cost_accounting.sqlite3`，但 2026-09-11 最终审计确认该 V1 库只有商品、映射和同步表，尚不存在 `basic_service_fee_rates`，因此它也不是截图中那份五列索引费率库。截图对应进程使用的数据目录仍需通过新增的绝对路径显示定位，不能猜测。

### 影响范围

- 所有从旧版本数据库升级、且旧表唯一索引未重建的环境，修改经营大类、导入相同四级类目但不同经营大类的官方规则，都可能在写入阶段失败。
- 用户看到的是数据库内部错误，无法判断是“真实重复版本”、数据库迁移问题，还是当前运行实例指向了旧数据目录。
- 当前业务语义下，同一经营大类、同一四级类目、同一生效日期仍应阻止重复；但不同经营大类即使四级类目和日期相同，也不应因旧索引而冲突。修复不能简单删除所有重复校验。

### 已实施解决方案（源码已修复，截图对应旧库尚待定位和实机验收）

- `connect_database()` 现在在执行现行建表脚本前检查 `basic_service_fee_rates` 的实际唯一索引；发现旧五列索引时，先生成 `before-service-fee-schema` 完整备份并通过完整性检查，再在事务中重建为 `(major_category, category_level_1, category_level_2, category_level_3, category_level_4, effective_from)`。旧记录 ID、费率字段、来源元数据和事件外键保持不变，失败时回滚并提示先完成兼容迁移。
- 桌面桥接状态和运行概览现在展示当前数据库绝对路径，客户端启动日志也记录同一路径，便于区分开发库、安装库和正式包数据目录。
- 重复版本提示已改为“相同经营大类、四级类目和生效日期已存在，请选择新的生效日期”，不再省略经营大类这一业务键。
- 新增旧五列索引迁移回归，验证迁移备份、六列唯一约束、旧 ID/费率/备注/事件保留、完整性检查和不同经营大类同日同类目可共存；新增重复版本业务提示回归。

### 当前结论

第一个问题的源码修复和自动回归已完成。当前未修改 `storage/` 验收库、V1.1 正式包或已安装客户端；已安装 V1 数据库 SHA-256 为 `A23215E4E40B12ED87ABE0A575E56FA6962453E034AC5A1DD96FC98B3922D042`，且无服务费表。仍需先由运行概览定位截图对应的实际旧费率库，再核对自动备份、六列索引和“空大类旧规则 → 生鲜新版本”写入，才可视为实机验收完成。

## 2026-09-10 测试发现问题 2：商品没有重量时整条真实成本被拦截

### 问题现象与证据

- 抖店活动页的多个商品规格没有可解析的重量，例如截图中的“5袋*1件、10袋*1件”等；扩展显示“商品重量未配置；商品类目未配置完整”，没有按通用模板首重 1 kg / 3 元计算。
- 当前业务口径是：商品没有重量时，按首重计费；现行通用模板即按 1 kg、3 元计入运费。这个运费仍是估算值，不应按 0 元处理。
- 问题截图：`C:\Users\23590\AppData\Local\Temp\codex-clipboard-c3daacf6-b1d2-41d7-b664-6d633bb051c2.png`。

### 根因确认

- 抖店导入只从“商品规格”文本中解析重量。`parse_specification_weight()` 找不到 `kg/公斤/g/克/斤` 等单位时返回 `weight_kg = NULL` 和“重量无法从商品规格确定”。
- `calculate_shipping_fee()` 遇到空重量直接返回“商品重量未配置”，没有使用模板的首重和首费作为业务默认值。
- `estimate_true_cost()` 把这个原因加入统一的 `unconfigured_reasons`；只要原因存在，就不生成真实成本结果。因此一个缺重量问题同时阻断了运费、真实成本和扩展拆解展示。

### 已实施解决方案（源码已修复，待实机验收）

- 运费计算在重量缺失时改用所绑定模板的首重和首费；有匹配的特殊地区规则时使用该地区独立首费。原商品 `weight_kg` 保持为空，不进行回写。
- `ShippingFeeEstimate` 和真实成本返回增加 `estimated_from_first_weight` 来源标记；扩展在完整和不完整成本卡片中都显示“估算运费（按首重估算）”，不会伪装为实际重量结果。
- 专项回归覆盖 0.5 kg、1 kg、1.1 kg、2 kg、2.1 kg、空重量基础首费和空重量特殊地区首费；通用模板空重量结果为 3 元。

## 2026-09-10 测试发现问题 3：抖店页面有商品类目，但服务费链路没有使用

### 问题现象与证据

- 截图中的抖店报名信息已经显示商品类目“休闲食品/糕点/点心/蛋黄酥”，但扩展仍显示“商品类目未配置完整”，基础服务费无法显示。
- 只读核对项目验收库发现，真实成本接口查询的映射记录中，截图商品对应的类目字段存在空的四级类目；当前验收库有 122,223 条已验证 SKU，其中 111,725 条四级类目不完整，38,350 条经营大类未配置。统计说明页面显示的类目和成本库保存的类目不是同一条数据链路。
- 问题截图：`C:\Users\23590\AppData\Local\Temp\codex-clipboard-c3daacf6-b1d2-41d7-b664-6d633bb051c2.png`。

### 根因确认

- 抖店扩展解析活动商品时，记录只保存商品 ID、商品名、SKUID、规格和最低到手价，没有保存页面上显示的商品类目。
- 真实成本请求只提交 `douyin_sku_id` 和 `lowest_price`；后端再从 `douyin_sku_mappings` 读取四级类目和经营大类。页面 DOM 中存在类目，并不会自动补入数据库映射。
- 导入程序严格把抖店导出表的四个类目列写入四个字段；缺失的第四级不会根据页面展示文本补齐，也没有在真实成本查询时使用页面类目作为临时匹配上下文。因此“控制台能看到类目”与“费率匹配能读到类目”目前是两件事。
- 真实成本计算和扩展展示还是“全有或全无”：只要服务费或运费任一缺失，后端返回 `available = false`，扩展只显示一条总的配置不完整提示，不显示已经查到的聚水潭成本。

### 用户确认的展示口径

- 成本库能找到聚水潭成本、但运费或基础服务费找不到时：继续显示聚水潭成本；运费显示“未找到”；基础服务费显示“未找到”；不生成虚假的真实成本和成本差额。
- 三项都找不到时也不能伪造金额；能查到哪一项就展示哪一项，缺哪一项明确标记未找到。

### 已实施解决方案（源码已修复，待实机验收）

- 扩展只从当前 SKU 侧栏中可验证的四个结构化类目节点读取页面路径，不按 `/` 字符猜测拆分；每条路径与 SKUID、最低到手价一起对齐传入新增的 `page_category_context_v1` 查询能力。

## 2026-09-10 测试发现问题 7：扩展偶发把本机成本服务显示为不可用

### 问题现象与证据

- 用户实测：成本服务窗口已经打开、服务实际可能仍在运行时，抖店浏览器扩展左下角偶尔显示“成本服务：不可用”。用户要求后续修复后必须在真实浏览器和真实服务进程下复查。

### 根因确认与可信度

- `browser_extension/content.js` 对整个抖店页面建立 `MutationObserver`，每次变化经 320ms 防抖后都发起一次 `GET_ACTIVITY_STATE`。代码只用序号防止旧结果覆盖新结果，没有取消或合并仍在执行的旧请求；活动页动态加载、打开抽屉和滚动都可能制造并发请求。
- `browser_extension/background.js` 每次请求先查 `/health`，再按每批 100 个 SKU 查询 `/api/v1/true-costs`；任意一批超时或返回非 2xx，整个调用就进入统一异常分支，并把所有当前卡片标记为服务不可用。请求固定 4.5 秒超时，没有重试、分批降级或沿用最近一次成功状态。
- `browser_extension/panel.js` 只要状态不是 `ok` 或 `limited` 就直接显示“成本服务：不可用”。因此一次请求超时、后台消息失败或旧请求异常，就会把瞬时网络/性能问题呈现成服务进程故障。
- 后端使用线程 HTTP 服务；真实成本接口对批次内每个 SKU 会多次读取数据库，而每次 `connect_database()` 还会执行完整建表脚本和兼容字段检查。没有实机耗时日志前，不能断言唯一是数据库慢，但“请求并发 + 固定超时 + 单批失败全局化”的误判链路已经由代码确认，数据库重复打开是高概率的超时放大因素。

### 已实施解决方案（源码与自动回归完成）

- 扩展侧已将同一页面刷新收敛为“一个执行中请求 + 一个最新待执行请求”；新结果仍按序号提交，页面频繁变化不再持续堆叠后台查询。
- 真实成本查询已按批次局部处理；网络错误和 5xx 最多重试一次，单批最终失败只标记该批商品，已成功批次继续展示。

- 左下角全局状态只根据 `/health` 和本机服务连接结果显示“已连接/不可用”；商品缺重量、类目、运费或费率只写入商品卡片的局部状态，不改变全局连接状态。
- 后端数据库读取性能与耗时测量仍归问题 8 单独处理，本条没有在缺少实机证据时调整 4.5 秒超时阈值。

### 二、代码和数据根因

- `basic_service_fee_rates` 只有四个类目字段，没有官方“大类”、通配规则、来源版本和导入校验信息；匹配要求四级文本完全相等，因此无法表达官方表中的 `/` 父级覆盖规则。
- 抖店商品映射保存商品导出的四级类目，但没有保存从官方费率目录推导出的“大类”。商品表没有大类时不能通过商品导入硬填或猜测。
- 现有费率页面按单条四级规则管理，无法展示完整的官方层级目录、规则覆盖范围和商品覆盖数量。
- `shipping_templates` 中的店铺和默认标记把可复用模板与店铺绑定在一起；缺少“店铺 + 商品ID → 模板”的独立关系。
- 整改前的 `true_cost` 在未显式传入模板时调用店铺默认模板；整改后正常业务路径按商品ID查绑定，未绑定明确返回未配置，不能按 0 计算。

### 三、已确认的业务口径

#### 服务费

- 适用范围：普通国内店基础技术服务费。
- 匹配条件：经营大类 + 商品四级类目；不增加第五级类目。
- 官方费率表中的 `/` 只作为费率规则通配符保存和匹配，不作为商品实际类目文本。商品导出缺少类目层级时保留未配置，不自动补全或猜测。
- `其他一级类目`至`其他四级类目`是同层精确类目均未命中时的兜底规则；优先级为“精确类目 > 其他 N 级类目 > `/` 父级覆盖”。缺失的商品类目层级只能由 `/` 覆盖，不能当作“其他”。
- 同一匹配程度下按生效日期选择版本。最新生效版本被停用时返回“已停用”，不能回退到旧版本。
- 特定渠道补充费率只展示官方来源信息，当前普通国内店成本计算不参与该费率。

#### 运费

- 绑定方式：店铺 + 商品ID → 运费模板；商品ID下全部规格共用模板。
- 通用模板：首重 1 kg、首费 3 元；续重 1 kg、续费 1 元；不足 1 kg 按 1 kg 计费；未命中特殊地区时使用基础价格。
- 验算口径：0.5 kg、1 kg、1.1 kg、2 kg、2.1 kg 分别为 3、3、4、4、5 元。
- “全国包邮”仅作为商品销售说明，不影响内部运费成本。
- 特殊地区使用独立的首重/续重价格，不在基础价格上叠加；页面支持后续增加北京等地区。本轮不预置任何特殊地区和金额。
- 商品未绑定模板、重量未配置、模板停用或地区规则无效时，真成本结果必须明确显示原因，不生成虚假的完整结果。

### 四、目标数据模型和页面行为

#### 基础服务费率

- 费率规则增加官方“大类”，保留四级类目字段；保存基础费率、可选的特定渠道补充费率、启用状态、生效日期、备注和版本信息。
- 官方目录导入保存来源文章 ID、官方更新时间、导入时间和规范化数据校验值；重复导入同一来源和校验值必须幂等，规则重复或字段不完整必须拦截。
- 商品映射保存四级类目，并保存由官方目录唯一推导出的经营大类；无法唯一推导时显示“经营大类未配置”，不自动选择。
- 服务费页面改为层级目录视图：支持经营大类筛选、类目搜索、费率筛选、生效版本、`/` 规则覆盖范围和商品覆盖数量；保留新增/停用、预览、确认、备份、事务写入、历史和回滚。
- 导入预览显示类目完整度、经营大类识别、费率命中、未配置和停用数量。匹配使用商品已知类目和官方 `/` 父级覆盖规则；末尾连续缺失的层级不伪造为具体类目，但在存在可覆盖父级规则时不能直接判定为未配置。

#### 商品运费模板

- 运费模板改为独立可复用资源，模板本体不再以店铺默认作为正常业务入口。
- 新增商品绑定关系，至少包含店铺名称、商品ID、模板ID、启用状态、创建/更新时间，并以店铺 + 商品ID保证唯一；同商品的 SKU 查询时共享该关系。
- 运费页面由“模板列表、商品绑定、地区价格编辑、重量费用预览”组成，显示模板使用商品数、未绑定商品数和地区覆盖情况。
- 模板编辑支持基础首重/续重、特殊地区独立首费/续费、启停和后续扩展；当前通用模板不写入特殊地区。
- 真成本计算正常路径按店铺 + 商品ID查绑定模板；现有 `shipping_template_id` 仅保留为内部诊断或显式覆盖能力，不作为默认兜底。

#### 成本结果

真实成本继续使用：

`聚水潭成本价 + 商品运费 + 最低到手价 × 基础技术服务费率`

其中最低到手价仍标记为估算基数。类目、经营大类、费率、重量或商品运费绑定任一缺失时，返回可解释的未配置原因。
