## 1. 系统职责

系统把聚水潭商品成本写入本机 SQLite，维护抖店 SKUID 到聚水潭商品编码的店铺映射，并在抖店活动页以只读夹板展示最低到手价和成本对比。桌面成本助手负责服务、状态、日志、商品资料和店铺映射管理。

```text
聚水潭普通表 + 组合表
          │
          ▼
Python 导入与校验 ──► SQLite + 启用商品 Excel + 更新备份
          │
          ├──► 127.0.0.1:8765 只读查询接口 ──► Edge 抖店只读扩展
          │
          └──► WebView2 桌面管理台
```

V2 正式包固定提供七个页面：运行概览、今日成本更新、抖店商品对应关系、更新历史、运行日志、基础服务费和运费模板。桌面页面通过受控桥接调用本机管理能力，浏览器只能查询。

V2 按 P0 → P1 → P2 实施：P0 保证类目费率、运费和真实成本口径正确；P1 增加基础服务费、运费模板管理和插件成本拆解；P2 修复扩展字体对比度。上述功能已进入七页正式包。

开发板源码共八页；正式分发包保留“基础服务费”和“运费模板”，只排除开发用途的“人工核验”页。“基础服务费”维护官方目录、经营大类、四级类目和生效版本；“运费模板”维护可复用模板、商品绑定和特殊地区独立价格；“人工核验”读取 `pending` / `conflict` 候选并以可恢复方式写入人工确认映射。

## 3. 数据模型

`products` 保存聚水潭当前商品资料：

- `sku_id`：文本主键，保留大小写和前导零；
- `name`：商品名称；
- `cost_price`：十进制字符串，可为空；
- `enabled`：商品状态；
- `autoid`、`created`、`modified`、`synced_at`：来源和同步审计字段。

`douyin_sku_mappings` 保存按店铺隔离的抖店 SKUID、聚水潭编码、状态、来源和时间字段。只有 `verified` 且目标商品启用的映射可以被成本夹板使用。

`mapping_import_batches` 和 `system_updates` 保存导入批次、文件哈希、完成状态、备份和可恢复关系。数据库保留待核验候选结构。V2 正式包不提供人工核验页；开发板可以使用该结构承接未能逐字符匹配的候选和跨店冲突。

### V2 数据与实现

V2 在不改变现有聚水潭成本快照和严格 SKU 映射规则的前提下，新增以下配置数据：

- 抖店 SKU 的一级至四级商品类目，来源为抖店商品表；开发板已实现导入、旧库迁移、待核验传递和成本快照重建保留；
- 商品/SKU 的重量；开发板已从确定的规格表达换算并保存千克值和解析来源，当前不含包装材料重量；
- 按“经营大类 + 四级类目”维护的基础技术服务费率、生效日期、启用状态、官方来源和备注；`/` 保存为父级通配规则，开发板管理页修改时新增版本，不覆盖旧版本；不同生效日期的记录保留为历史，旧无大类规则采用可恢复归档，不做物理删除；
- 可复用运费模板、特殊地区规则、首重和续重；通过“店铺 + 商品ID”唯一绑定模板，同商品下全部 SKU 共用；
- 配置版本、更新时间、操作记录和恢复关系。

基础服务费不按销量或特定渠道补充费率匹配。官方目录可由管理台预览后幂等导入；商品类目导入后先按一级类目唯一推导经营大类，再按“精确类目 > 其他 N 级类目 > `/` 父级覆盖”的优先级匹配。无法唯一推导或未匹配不得按 0% 处理。

抖店活动页即时读取到的类目只作为本次真实成本查询的临时匹配上下文，不回写 `douyin_sku_mappings`；商品导入的一级至四级类目仍按独立字段保存。四级类目拆分不改变聚水潭成本价按 `jushuitan_sku_id` 关联 `products.sku_id` 的逻辑。`休闲食品/糕点/点心/蛋黄酥` 应按四级独立路径处理，并允许官方 `休闲食品////` 父级规则覆盖末尾缺失层级。

当前项目验收库 `storage/test/cost_accounting.sqlite3` 已依据抖店官方《2026基础技术服务费费率标准》写入 270 条完整规则，生效日期记录为官方页面更新时间 2026-07-15；同时保存文章 ID、官方更新时间、导入时间和规范化 SHA-256。旧的 41 条人工版本保留为历史。官方目录导入使用一个事务、一个系统更新记录和一份写入前备份；重复导入同一校验值不重复写入。

## 4. 商品表导入

普通商品表必需字段为：`商品编码`、`商品名称`、`成本价`、`商品状态`。一行代表一个普通商品，成本价为空时保持为空。

组合商品表必需字段为：`组合商品编码`、`组合商品名称`、`组合成本价`、`商品状态`、`商品编码`、`数量`、`子商品成本价`。原表一行是子商品明细，程序按组合商品编码折叠；`组合成本价`是权威成本，子商品成本合计只用于检查。

聚水潭导出文件可能在编码中保存 SpreadsheetML `_xNNNN_` 转义。程序在目录入口对标准转义单次解码，再做重复、冲突和跨表检查；不会改大小写、内部空格或其它业务字符，也不会递归解码受保护的字面转义。

两份商品表必须来自同一个日期。程序优先使用 XLSX 工作簿的创建时间作为导出日期，不使用商品行的最近修改字段，避免同一批导出中因单行修改时间不同而被误判；缺少创建时间时不凭行级字段猜测日期。预览阶段只读解析并展示数量、空成本、重复、冲突和相对当前库的变化；确认阶段重新读取同一文件并核对哈希，创建一致性备份后以一个 SQLite 事务发布商品快照和启用商品 Excel。任何一步失败都保留上一份完整数据。

## 5. 店铺映射

店铺名称由操作者明确输入或选择，程序不从文件名、商品名或规格推断店铺。抖店 `规格ID（SKUID）` 是店铺侧唯一键，`商家SKU编码` 只有与启用聚水潭编码逐字符相等时才进入验证映射。V2 要求抖店商品表提供商品类目，类目随已验证的 SKU 映射保存，用于匹配基础技术服务费；类目不是 SKU 严格匹配的替代条件。

导入规则如下：

1. 预览完整店铺文件，报告总行、精确匹配、待核验、重复/无效、新增、更新和移除，并统计精确匹配行的类目完整度与当前基础费率覆盖。
2. 跨店相同 SKUID、同一 SKUID 多目标、重复或无效标识阻止确认。
3. 新店铺新增映射；已有店铺用完整文件替换该店，其他店铺不变。
4. 确认前创建备份，确认时重新检查店铺名、文件哈希和预览凭证。
5. 写入完成后核对目标商品存在且启用，并记录系统更新。

开发板当前要求抖店表明确包含 `一级类目`、`二级类目`、`三级类目`、`四级类目` 四列。各级文本只去除首尾空白后分别保存，不使用 `/` 拼接，避免类目名称自身包含 `/` 时丢失层级；缺少的末级保存为空字符串。类目变化属于店铺映射更新，待核验记录人工确认后沿用原导入类目。

名称、规格、价格和相似度只用于人工查看，不能作为自动匹配依据。

开发板导入预览已报告精确映射行的类目完整/缺失、当前基础费率已匹配/未配置/已停用数量。该统计只读且不改变映射导入资格。类目字段的实际表头以当前抖店导出文件为准；程序只接受确定的字段名或明确登记的兼容别名，不对任意相似表头做模糊猜测。

当前真实数据基线选用每家店日期最新的文件：`铭香馆9.8.xlsx` 严格映射 23,250 条、待核验 51 条；`忆百草小店9.5.xlsx` 严格映射 59,812 条、待核验 137 条。两批已写入项目验收库并通过写后完整性检查，未同步到已安装的 V1.1 客户端。

开发板的人工核验只允许操作者明确填写目标聚水潭编码，不能由页面自动猜测。页面最多读取最近 200 条开放记录，冲突优先；目标编码不存在、未启用、记录已处理或原映射在保存后发生变化时，操作会被拒绝并要求重新导入最新店铺表。

## 6. 本机查询与 Edge 扩展

服务只监听 `127.0.0.1:8765`。浏览器可使用的接口只有：

```text
GET /health
GET /api/v1/mappings?douyin_sku_id=...&douyin_sku_id=...
GET /api/v1/products?sku_id=...&sku_id=...
GET /api/v1/true-costs?douyin_sku_id=...&lowest_price=...

批量查询使用重复参数，避免 SKU 编码本身包含逗号时被错误拆分；服务端仍兼容旧版逗号分隔参数。
GET /api/v1/products/<sku_id>
```

管理预览和写入只通过桌面页面的白名单桥接执行，不能向普通网页开放管理 POST。

开发板已新增成对重复参数的只读真实成本接口，按抖店 SKU 和最低到手价返回聚水潭成本、重量、经营大类、商品类目、商品绑定运费、基础服务费率、真实成本及差额。后续修复必须允许请求附带页面临时类目，并把聚水潭成本、运费、基础服务费作为独立组件返回：已找到的成本价不能因其他组件缺失而隐藏，缺失组件显示“未找到”，只有组件齐全时才计算真实成本和差额。`/health` 通过 `true_cost_breakdown_v1` 能力标识兼容新旧扩展数据流；每批最多 100 条。管理台的基础服务费、运费模板和商品绑定保存继续采用预览、确认、备份、原子写入和回滚；扩展不具备配置写入权限。

开发板基础服务费数据层使用 `service_fee_catalog_imports` 保存官方批次，使用 `basic_service_fee_rates` 保存经营大类、四级类目、基础费率、特定渠道展示费率、生效日期、启停状态、可恢复归档状态和来源，使用 `basic_service_fee_rate_events` 追加新增及启停记录。匹配先排除归档记录、限定经营大类，再按精确匹配、“其他 N 级类目”兜底、`/` 父级覆盖的顺序选择规则，并取查询日期当日或之前的最新版本；最新版本停用时明确返回原因，不回退旧版本。无经营大类旧规则只能在确认没有有效商品引用后，经预览、备份和事务归档；记录及事件保留并由系统更新回滚恢复。成本快照重建会复制目录批次、费率版本、归档状态和事件记录。

扩展只在抖店活动页和商品编辑页工作。活动页读取操作者打开的 SKU 侧栏当前页面区域中的平台 SKUID、规格和“最低到手价”；商品编辑页读取同一行的 SKUID 与商家编码用于建立可审计观察。页面结构不符合要求、字段缺失、重复或价格为区间时，扩展停止该条计算并显示原因。

扩展先按平台 SKUID 查询已验证映射，再按聚水潭编码查询商品成本。查询按每批最多 100 条拆分；没有精确映射、成本缺失或成本为零时不显示看似有效的计算结果。扩展左下角“成本服务”只表示本机服务连接，批次超时或单商品配置缺失不能升级为全局服务不可用；页面刷新请求必须合并或取消旧请求，避免动态 DOM 变化造成状态误判。

## 7. 当前 V2 成本计算

历史 V1 夹板使用以下十进制算法：

```text
涨跌额 = 最低到手价 - 聚水潭成本价
较成本涨跌率 = 涨跌额 / 聚水潭成本价 × 100%
```

该历史结果显示正负号并保留两位小数，但不包含运费和平台服务费，因此不称为毛利率、利润率或净利润率。

当前 V2 采用以下已确认的估算口径：

```text
基础服务费估算基数 = 最低到手价
基础技术服务费 = 最低到手价 × 商品类目基础费率
真实成本 = 聚水潭成本价 + 估算运费 + 基础技术服务费
成本差额 = 最低到手价 - 真实成本
较真实成本涨跌率 = 成本差额 / 真实成本 × 100%
```

V2 运费模板采用地区 + 重量模型：商品/SKU 保存当前由规格确定的净含量重量，模板独立保存首重、续重和特殊地区价格，`shipping_product_bindings` 以“店铺 + 商品ID”唯一绑定模板。同一商品下全部 SKU 共用模板；未命中特殊地区时使用基础规则，特殊地区首费/续费独立替换基础价格。“全国包邮”只属于销售说明，不改变内部成本。无重量时按模板首重/首费估算，通用模板按 1 kg / 3 元，界面标注“按首重估算”，不写回实际重量。商品绑定、经营大类、类目或基础费率缺失时，分别显示明确原因；已找到的聚水潭成本价仍可单独显示，只有组件齐全时才生成完整成本结果。

现有运费模板结构尚不能表达“不发货/禁运地区”。项目验收库当前使用一个全国通用模板：首重 1 kg / 3 元、续重 1 kg / 1 元，无特殊地区，已绑定全部 10,806 个店铺商品组合。北京等特殊地区金额待用户明确后再配置。

V2 插件展示聚水潭成本、运费、类目基础费率、基础技术服务费、真实成本、最低到手价、成本差额和涨跌率，并将结果标为估算。V2 不计算销量阶梯、特定渠道补充费率、达人佣金、广告费、税费或售后损耗。

费率查询以用户确认的抖店基础服务费表为业务依据：[基础服务费查询](https://school.jinritemai.com/doudian/web/article/ahijyoja6hvb?btm_show_id=feefe42e-699e-4130-98cd-714de1f4769d)。当前官方快照作为带来源和校验值的数据资源内置，不把费率写进计算代码；平台费率变化时更新数据资源并通过管理台导入新批次。

## 8. 聚水潭 API 设计边界

API 客户端已经具备签名、分页、重试、时间窗口和环境校验代码，但当前正式 API、权限、令牌和正式数据验收暂不启用。测试环境只能证明程序流程，不能证明当前商家数据。

设计的主要接口是 `/open/sku/query`：按不超过七天的创建或修改时间窗口分页读取商品资料，使用 `sku_id`、`autoid`、启用状态和成本价形成当前快照。正式启用前必须完成应用资质、接口权限、令牌生命周期、全量同步、数量核对和真实商品抽查。

测试和生产配置严格分离：测试只允许 `https://dev-api.jushuitan.com`，生产只允许 `https://openapi.jushuitan.com`。密钥和令牌只存在本机配置，不写入日志、扩展、Excel 或文档。

## 9. 安全与恢复

- 上传文件限制扩展名、压缩大小、解压大小、条目数和数据行数。
- 预览不写库；确认只能使用同一次预览产生的不可猜测凭证。
- 确认时重新读取文件并复核哈希。
- 每次写入先备份，再用事务发布；数据库完整性检查失败时停止。
- 更新历史只允许回滚全局最新一次成功系统更新。
- 扩展只读展示，不执行抖店业务操作。
- 安装器不读取或伪造 Edge 用户配置，不写企业扩展策略。
