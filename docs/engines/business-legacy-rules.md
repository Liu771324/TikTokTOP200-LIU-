## 0. 当前结论

当前正式工作目录是 `商机中心`。`collect_v4.js` 是当前正式采集器，`备份/` 只是旧基线，不能当作运行目录。

当前已确认的最终路线：

- 使用真实 Microsoft Edge 的远程调试端口连接抖店。
- 不导入 Cookie，不复制和解密 Edge 用户目录。
- 使用 aurora 页面结构对应的选择器和真实底部分页。
- 使用固定等待 + 真实内容前后对比 + 有上限的完整流程重试。
- 不刷新页面，不重复点击已经被页面接收的下一页。
- 页面异常时宁可明确失败，也不能用旧 DOM 或空数据生成看似正常的报告。

多类目自动扫描和批量接续已经接入正式流程；批量层不能改变下面已经验证过的单类目采集红线。

## 1. 业务口径

### 1.1 目标

从抖店商机中心指定类目中，按近 30 天成交金额档位筛选商品，进入详情读取“近1天”的成交金额和较上周期增长，输出今天成交高于昨天的商品。

当前报告字段：

```text
产品名称 | 近30天总成交 | 昨日成交 | 今日成交 | 较昨日增长
```

多类目改造后必须增加：

```text
类目 | 产品名称 | 近30天总成交 | 昨日成交 | 今日成交 | 较昨日增长
```

### 1.2 页面入口

正式入口：

```text
https://fxg.jinritemai.com/ffa/bu/NewBusinessCenter
```

早期文档中出现过 `fxzg.jinritemai.com`，那是历史记录中的域名笔误，不要恢复使用旧地址。

### 1.3 时间口径

详情抽屉中必须选择“近1天”：

| Tab | 较上周期含义 | 是否用于昨日反推 |
|---|---|---|
| 近1天 | 今天 vs 昨天 | ✅ 是 |
| 近7天 | 本周 vs 上周 | ❌ 否 |
| 近30天 | 本月 vs 上月 | ❌ 否 |

不要把近7天或近30天的变化当成今日对昨日。

## 2. 登录和浏览器：不要重新发明方案

### 坑1：Playwright Chromium 的 DNS 失败

**现象：** 浏览器报 `ERR_NAME_NOT_RESOLVED`，无法访问 `jinritemai.com`；系统 `curl` 或 `nslookup` 可以解析。

**根因：** Playwright Chromium 在 Windows 上使用的异步 DNS 解析路径在中国网络环境中可能失败。

**历史临时方案：** 曾尝试 `--host-resolver-rules` 映射 IP，但不应成为当前主方案。

**当前正确方案：** 连接真实 Edge，让 Edge 使用系统 DNS。

### 坑2：不要依赖浏览器工具封装的自定义启动参数

某些浏览器工具无法可靠传入自定义启动参数。当前项目直接通过 `edge.js` 查找或启动 Edge，再由 Playwright CDP 连接，不依赖外部浏览器封装。

### 坑3：Cookie 导入会破坏登录态

**现象：** 从 DevTools 复制 Cookie，设置到另一个 Playwright 浏览器后，仍然被重定向到登录页，甚至用户原来的 Edge 登录态也被顶掉。

**根因：** 抖店会校验设备指纹、TLS、会话上下文等；Cookie 不是可跨浏览器迁移的完整登录态。

**硬性结论：**

- 禁止导入抖店 Cookie。
- 禁止复制、解密或迁移 Edge 用户目录。
- 禁止尝试 Playwright Chromium 直接复用 Edge profile。
- 只能连接用户已经登录的真实 Edge CDP 会话。

### 坑4：Edge 默认用户目录不能用于远程调试

Edge 会拒绝在默认用户数据目录下开启远程调试，并提示：

```text
DevTools remote debugging requires a non-default data directory.
```

必须使用独立目录，例如：

```text
--remote-debugging-port=9222
--user-data-dir=%TEMP%\edge-debug
```

### 3.1 页面必须先进入列表视图

**硬性要求：** 先点击“列表”视图。没有进入列表视图时，经典商机数据表可能不存在，后续读取会得到空数据。

### 3.3 Cascader 交互

直接对 `#category` 使用普通 Playwright click 曾被 label 或组件层拦截。

当前可靠思路：

1. 在页面上下文中定位真实 input。
2. 使用原生 `input.click()` 和 `input.focus()`。
3. 触发 React 能识别的 input 事件，填入搜索词。
4. 等待菜单真实出现。
5. 对菜单文本做空格归一化，例如把 `传统滋补 / 药食同源食品` 与 `传统滋补/药食同源食品` 统一比较。
6. 点击目标菜单项后，重新读取输入框或页面状态确认选择成功。

未来自动扫描类目时，参考 TOP200 的“遍历 Cascader、保存完整路径和 segments”思路，但不能直接复制 TOP200 的 DOM 选择器。

## 4. 坑5：假分页

**现象：** 点击顶部分页后，页码文字发生变化，但商品数据没有变化；有时没有任何新的网络请求。

**根因：** 页面同时存在两个分页组件：

- 顶部自定义分页：看起来会翻页，但可能只是显示状态。
- 底部 `.aurora-pagination`：实际驱动商机数据表更新。

**错误做法：** 只判断页码从 1 变成 2，就认为翻页成功。

**正确做法：**

1. 固定使用真实底部分页。
2. 翻页前记录活动页码、商品名、金额和完整行数。
3. 点击下一页最多一次。
4. 等待目标页码出现。
5. 继续等待商品/金额指纹真正变化。
6. 确认原始行数、完整行数和商品内容完整后再读取。

如果页码已经变化但内容仍是旧页，只能等待，不能再次点击下一页，否则会跳过一页。

## 5. 坑6：条件等待误判旧 DOM（最重要）

这是之前最容易被“优化”重新引入的问题。

### 5.1 错误改法

曾把固定等待改成以下形式：

```js
await page.waitForFunction(() => {
  const tbody = document.querySelectorAll('.aurora-table-tbody')[3];
  return tbody?.querySelectorAll('.name-PRUTXd').length >= 3;
});
```

这在 React SPA 中不可靠，因为翻页时旧页面的 DOM 节点仍然存在，旧商品名数量已经满足条件；条件会立即通过，但新数据尚未渲染。

### 5.2 实际故障链

```text
旧 DOM 仍存在
  → 条件等待立即返回
  → 脚本点击即将被替换的旧商品节点
  → click 落在旧节点/空气上
  → 抽屉没有打开
  → 100 条只得到约 5 条
  → 采集耗时从约 542 秒恶化到约 971 秒
```

翻页后“第一行已存在”“行数大于 1”“商品名数量大于 3”都不能单独证明新页面已经准备好。

### 5.3 当前正确原则

不要为了追求速度，把所有固定等待替换成 `waitForFunction` 或“节点存在”判断。当前项目应采用：

```text
固定等待
  + 活动页码/商品名/金额/行数前后对比
  + 有上限的完整流程重试
```

尤其不能删除以下关键等待，除非有真实页面证据和回归测试：

- 排序后的页面稳定等待。
- 翻页后的数据稳定等待。
- 翻回商品所在页后的数据稳定等待。
- hover/click 后抽屉出现等待。
- 切换近1天后详情数据加载等待。
- 关闭抽屉后的消失等待。

条件等待可以作为“提前结束”的辅助，但不能只依赖旧 DOM 的存在；应与前后指纹和固定最小等待结合。

## 6. 坑7：排序方向检测

### 6.1 顶部并列档位会误判

商机中心成交金额是档位，顶部可能连续很多行都是 `¥1000万-¥2500万`。如果只比较第一行和第八行，会误认为没有降序：

```text
第一行 == 第八行
→ 错误判断排序未生效
→ 多次点击
→ 可能从降序再次点到升序或 none
```

### 6.2 正确判断

排序验证至少需要：

- 先读取成交金额表头的 `aria-sort`，并兼容上下箭头的 `active` 状态。
- 当前已是 `descending` 时禁止再次点击。
- 可解析的金额档位从上到下必须非递增；连续相同档位是合法降序。
- 不能把“小于某金额”这类特殊值简单当成普通 0 值干扰判断。

不要依赖“点击第几次一定是降序”，真实页面已验证会在 `descending → ascending → none → descending` 之间循环。

### 6.3 排序日志冒号后为空：先查表格定位，不要继续点排序

**发生时间：** 2026-08-25。

**故障特征：**

```text
排序尝试 1:
排序尝试 2:
排序尝试 3:
排序尝试 4:
采集失败：无法确认成交金额已降序
```

冒号后完全没有金额，说明程序没有读到商品行。这不是普通的“升降序判断错误”。

**真实根因：**

1. 旧代码把商品表写死为 `document.querySelectorAll('tbody')[3]`。
2. 页面更新后只剩 1 个 `tbody`，真实商品表是索引 0。
3. 当时页面表头已经是 `aria-sort="descending"`，但旧代码仍连续点击排序控件，既无法读取金额，也可能把正确降序切走。

**永久规避规则：**

- 禁止依赖页面有几个 `tbody`、商品表排第几个。
- 商品表必须按“搜索词 + 成交金额”表头定位。
- “成交金额”列号必须从表头计算，禁止永久写死为 `cells[3]`。
- 表体首行可能是隐藏表头占位行，应按结构识别并排除。
- 排序前先读状态，只有不是降序时才点击。
- 排序确认要求“页面声明降序 + 金额档位非递增”同时成立。
- 日志金额数组为空时，应明确报“未读到商品行/未定位到商机数据表”，不能盲点四次。
- 修改表格或排序选择器后，必须连接真实 Edge 做排序三态循环，并最终检查整页恢复降序。

**防回归位置：**

- 实现：`business_table.js`
- 调用：`collect_v4.js`
- 测试：`test/business_table.test.js`
- 真实验证：30 条商品全部读取，第一条 `¥7500万-¥1亿`，最后一条 `¥1000万-¥2500万`，整页非递增，最终状态 `descending`。

## 7. 坑8：增速快标签会被当成成交金额

### 7.1 错误页面结构假设

不能假设指标卡永远是：

```text
指标名
数值
较上周期
百分比
```

实际可能是：

```text
成交金额
增速快
¥10万-¥25万
较上周期
49.10%
```

### 7.2 错误结果

如果取“成交金额”后的第一行，今日成交会被读取为 `增速快`，导致：

- 报告的今日成交整列错误。
- 大量商品被归入无法读取。
- 增长统计失真。

### 7.3 正确解析

- 读取成交金额时，跳过描述标签：`增速快`、`持平`、`需求大`、`竞争小`、`热度高` 等，取第一个有效金额档位。
- 读取增长值时，不要无条件过滤掉 `增速快` 或 `持平`，它们可能是合法业务状态。
- `999.99%+` 需要视为下界/上限表达，而不是普通精确数字。
- 增长方向不能只看百分比数字正负；见下一节。

## 8. 坑9：增长方向不能只看百分比符号

aurora 抽屉的“较上周期”百分比可能永远显示为无符号数字，方向由 CSS 类名、箭头或颜色表达。

例如页面可能显示：

```text
25.4%
```

但它可能是下降；不能用 `parseFloat(value) > 0` 直接判定增长。

正确排查顺序：

1. 读取趋势箭头或趋势容器 class。
2. 识别 `trendArrowUp` / `trendArrowDown`、`trendValuePositive` / `trendValueNegative` 等已验证 class。
3. 把方向和数字分开解析。
4. 对页面改版后的真实 DOM 做 fixture 和真实只读验证。

曾经出现过商品实际下降 25.4% 却被错误判定为增长的情况。这个问题不能重新引入。

### 8.1 列表“成交增速”的真实箭头结构

2026-09-16 对已打开的真实商机中心列表做只读验证：

- 商品表表头包含“成交增速”，当前位于第 5 列。
- 数据行没有可用于方向判断的趋势 class 或 aria 标签。
- 方向由 8×8 SVG 箭头和 `path fill` 表达：红色向上为 `#FF3B52`，绿色向下为 `#00C87F`。
- 百分比文本仍然不带正负号；例如红色向上显示 `1.08%`，绿色向下显示 `50.41%`。

因此近 30 天预筛选必须读取 SVG 箭头状态，不能回退到百分比数值。缺少“成交增速”列时应明确失败；单行箭头无法识别时应跳过并计入预筛选跳过数，不能计入详情失败。

## 9. 坑10：网络慢和长流程详情失败

### 9.1 历史现象

2026-08-03「滋补养生原料」一轮：

- 664 条达标。
- 271 条增长。
- 90 条未完成。
- 78 条读不到成交金额/增幅。
- 12 条两次点击后抽屉仍未打开。
- 耗时约 3757 秒。

### 9.2 根因

- 抽屉打开了，但近1天数据还没加载就被读取。
- 所有商品使用同一组等待，后段网络变慢后等待不足。
- 翻页只比较第一条商品，下一页尚未完全渲染就开始读取。
- 页码先变、数据后变时，重复点击导致跳页。

### 9.3 正确修复策略

单个商品每次重试都必须完整执行：

```text
重新定位当前 DOM
  → 打开抽屉
  → 确认抽屉是目标商品
  → 切换近1天
  → 等待成交金额和增长加载
  → 读取并分类
  → 关闭抽屉
```

最多三次，等待递增。不能复用旧的商品节点、旧抽屉或旧读取结果。

分页状态至少保存：

- 活动页码。
- 分页器明确页大小。
- 原始行数和完整行数。
- 全页商品名指纹。
- 全页金额指纹。
- loading 状态。

分页三次仍无法确认时，整轮应明确失败并保留上一份完整报告；单商品三次失败则记录失败原因并继续其他商品。

## 10. 停止、暂停和报告不能回退

### 10.1 不要直接 kill 子进程

Windows 下不能依赖 `SIGTERM` 处理器可靠保存内存中的结果。停止操作必须使用独立停止标记文件：

1. 服务端为本轮采集创建独立 `STOP_FILE`。
2. 点击停止时写入标记并解除暂停。
3. 采集器在安全边界检查标记。
4. 当前商品处理完成后统一收尾。
5. 生成明确的部分 Markdown、JSON 和 Excel。

### 10.2 两种完整性必须分开

```text
已处理数据完整性：例如 128/128
区间覆盖：已完成 / 未完成
```

停止时即使已经处理的数据分类守恒，也不能把整个金额区间标记为已完成。

### 10.3 文件规则

完整报告不能被部分报告覆盖：

```text
选品报告-成交增长.md
选品报告-成交增长.xlsx
选品报告-成交增长-部分.md
选品报告-成交增长-部分.xlsx
```

用户停止、显式页数/商品上限触发且区间未覆盖时，生成部分报告并写明原因。页面结构异常、分页不可信、行数据不完整或分类守恒失败时，不能生成可能误导用户的部分报告。

## 11. 数据解析和金额边界

### 11.1 严格金额解析

支持：

```text
小于¥50       → min=0, max=50
¥500-¥750     → min=500, max=750
¥1万-¥1.5万   → min=10000, max=15000
¥25万-¥50万   → min=250000, max=500000
```

空值、加载文案、乱码、倒置档位和无法识别的内容不能静默转换成 0。

### 11.2 区间规则

用户设置 `1万—25万` 时：

```text
档位高于/跨越上限 → 跳过详情，继续翻页
完整落入区间       → 打开详情并归类
低于/跨越下限      → 停止向后扫描
```

边界在平台档位中间时，跨边界档位排除，不扩大用户指定范围。

## 13. 给下一个 AI 的排障顺序

遇到“采集为空、少数据、抽屉打不开、翻页重复或增长方向错误”时，按顺序检查：

1. Edge 是否通过真实 CDP 连接，是否仍在登录页。
2. 是否进入列表视图。
3. 是否选中了正确类目，选择后是否触发查询/刷新。
4. 是否按“搜索词 + 成交金额”表头定位真实商品表，是否仍残留固定 `tbody` 索引。
5. 是否使用底部真实分页。
6. 是否误把旧 DOM 存在当作新页面已加载。
7. 是否重复点击了已经接收的下一页。
8. 是否把描述标签当成成交金额。
9. 是否只看百分比数字而没有读取增长方向 class。
10. 是否使用了过短的抽屉/近1天等待。
11. 是否复用了旧商品节点或旧抽屉。
12. 是否在停止时直接杀死进程导致报告丢失。

先定位属于哪一类已知问题，再做最小修改；不要直接大规模重写等待、选择器和采集流程。

## 14. 多类目改造的额外红线

多类目任务可以参考 `Tiktok TOP200` 的：

- `collector.js` 的 `discoverCategories()`、`discoverOptions()`、`runTask()`。
- `task-store.js` 的 `createTask()`、`saveTask()`、原子 JSON 写入。
- `server.js` 的发现缓存和任务参数校验。
- `public/index.html` 的搜索、多选、任务进度和历史任务。

但不能直接复制：

- TOP200 的榜单、品牌、周期、TOP200 排名逻辑。
- TOP200 的 DOM 选择器。
- TOP200 的商品链接和 Excel 分榜单逻辑。

多类目实现必须保持本文件的所有单类目稳定性规则，尤其是固定等待、分页前后指纹、抽屉完整重试、分类守恒和协作式停止。

## 15. 沟通和修改规则

- 用户是抖店商家，偏好简洁、明确、可操作的说明。
- 涉及登录、Cookie、真实大规模采集时，先确认再执行。
- 新增功能先写方案并确认，不擅自改变采集口径。
- 不能为了“性能优化”删除固定等待，除非有真实页面证据、脱敏 fixture 和回归测试。
- 不能把一次成功试跑当成页面结构永久稳定。
- 完成修改后必须说明：改了什么、保留了哪些红线、测试结果是什么、真实页面是否验证过。
