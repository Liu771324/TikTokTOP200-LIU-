# 商机中心 API 单类目全量分类采集技术方案

> 文档状态：当前项目正式技术方案
>
> 适用目录：`商机中心--后端加速版`
>
> 最后更新：2026-08-28
>
> 目标：使用 API 完成单类目、可配置最低成交金额的全量采集，并输出与上级目录“商机中心”一致的数据口径。

## 1. 方案定位

本项目是上级“商机中心”采集系统的单类目 API 换代升级版：

- 一次任务只采集一个类目节点；
- 前端选择类目和最低成交金额；
- 达到最低金额的商品全部保留，不只保留上涨商品；
- 通过 `real_time_list` 和 `indicator` API 获取数据；
- 最终报告沿用参考 Excel 的核心字段、金额档位和增长口径；
- Edge 只承担登录态和页面上下文，数据读取尽量通过 API 完成。

本方案不复制上级项目的多类目批量任务、逐商品打开详情抽屉和多进程采集逻辑。

## 2. 用户功能

### 2.1 前端页面

页面提供：

1. 类目树读取、搜索和选择；
2. 当前选中类目的完整路径展示；
3. 最低成交金额输入，例如 `10000`、`750000`；
4. 创建单类目采集任务；
5. 查看当前页码、已采集数量、分类统计和失败数量；
6. 暂停、继续、停止并生成部分报告；
7. 对失败商品进行重试；
8. 下载 Excel、Markdown 和 JSON 报告。

### 2.2 类目规则

- 允许选择一级、二级或叶子节点；
- 选择父节点时，采集该节点及其子类目；
- 任务必须保存完整类目路径、节点 ID 和类目层级；
- 不允许使用只保存名称的类目参数，避免重名类目采集错误；
- 类目树优先从商机中心类目接口读取，不能要求用户长期手工维护静态 `categories.json`。

类目 API 的真实请求参数必须以已登录页面产生的请求为准。当前已确认一级类目使用 `first_cid`；子类目参数在开发时必须通过真实请求或脱敏 fixture 确认后再实现，不能凭字段名称猜测。

## 3. 认证和风控边界

### 3.1 默认路线：Edge 页面上下文 API

默认通过已登录的真实 Edge 页面上下文执行 `fetch`：

- Cookie、来源页、User-Agent 和浏览器网络环境保持一致；
- 不复制、解密或迁移 Cookie；
- 不打开商品详情、不反复点击分页、不刷新商机中心页面；
- 采集数据主要来自 API，降低页面操作量。

Edge 页面上下文路线只能降低登录态和客户端特征不一致的风险，不能保证不触发平台限流或风控。

### 3.2 备用实验路线：`cookie.txt` 直连 API

`cookie.txt` 直连路线仅作为独立实验或备用路线：

- 不与 Edge 页面上下文路线混合采集同一个任务；
- Cookie 只由用户手工放入本地文件；
- 不写入日志、报告、检查点或前端响应；
- 不提交 Git；
- Cookie 过期、接口返回登录页或 `401/403` 时立即停止并提示更新。

直连 API 同样不能承诺零风控。请求频率、并发、IP、会话和客户端特征仍可能被平台识别。

两种路线对比时，使用相同类目、相同金额阈值、相同页数和相同并发设置，先只测试 1～3 页，再决定是否启用备用路线。

## 4. API 接口

### 4.1 商机列表接口

```text
POST /api/commop/business_chance_center/clue/common/real_time_list
Content-Type: application/json
```

基础请求体：

```json
{
  "condition": {
    "categories": [{"first_cid": 1000002718}],
    "hit_clue_label_ext": true,
    "show_new_supply_link": true,
    "include_hot_sales_products": true,
    "sort": {"sort_direction": 1, "sort_field": "TRADING_AMOUNT"}
  },
  "clue_type": "",
  "clue_type_new": 11,
  "page": {"current": 1, "page_size": 18},
  "terminal_type": 0,
  "source": "business_center"
}
```

要求：

- `sort_direction=1` 表示成交金额降序；
- `sort_field=TRADING_AMOUNT` 表示按近 30 天成交金额排序；
- `page.current` 从 1 开始；
- `page.page_size` 默认 18；
- 类目参数必须来自前端选择的完整类目对象；
- 读取列表后保存原始响应和解析后的商品记录。

商品列表重点字段：

```text
clue_detail.clue_id
clue_detail.name
clue_detail.category_path
clue_indicator.pay_amount_ind
clue_indicator.pay_amount_ind_range
```

### 4.2 指标接口

```text
POST /api/commop/business_chance_center/clue/common/indicator
Content-Type: application/json
agw-js-conv: str
```

请求体：

```json
{
  "clue_id": 67803642,
  "recently_day_type": 1
}
```

只使用 `recently_day_type=1`，即近 1 天口径。

重点字段：

```text
data.pay_amount
data.pay_amount_hb
data.pay_amount_range
data.search_pv_cnt
data.demand_supply_rate
data.online_prod_cnt
```

指标响应必须和请求中的 `clue_id` 绑定保存，不能把并发请求结果按返回顺序盲目写回商品。

## 5. 采集流程

```text
读取类目树
  ↓
用户选择一个完整类目路径和最低成交金额
  ↓
创建单类目任务并保存任务快照
  ↓
按近30天成交降序读取列表页
  ↓
读取每条商品的近1天指标
  ↓
校验字段、解析金额和增长方向
  ↓
保存检查点
  ↓
达到停止条件后合并、分类并生成报告
```

每页处理规则：

1. 拉取列表页并校验响应为 JSON；
2. 校验页码、商品数量、商品 ID 和成交金额字段；
3. 对本页商品按批次调用指标接口，默认每批最多 6 个并发；
4. 每个指标结果按 `clue_id` 写回；
5. 保存原始响应、解析字段、失败原因和更新时间；
6. 保存检查点后等待约 20 秒再翻下一页；
7. 当前页全部商品低于最低金额后停止继续翻页。

列表按成交金额降序排列，因此不能使用“遇到一条低于阈值就立即停止”的未经校验逻辑。必须先确认当前排序有效，并处理档位相等、空值和解析失败情况。

## 6. 数据校验和分类

### 6.1 金额档位

金额档位保留平台原始展示文本，例如：

```text
¥10万-¥25万
¥100万-¥250万
小于¥50
```

最低金额判断使用档位下限，不把无法解析的金额静默转换成 0。档位解析失败的商品进入重试和失败记录流程。

### 6.2 参考输出字段

每条成功商品至少保存：

```text
类目
产品名称
近30天总成交
昨日成交
今日成交
较昨日增长
分类
```

### 6.3 分类规则

分类必须基于经过校验的原始 `pay_amount_hb` 和趋势方向：

| 分类 | 条件 |
|---|---|
| 下跌 | 环比方向为下跌，且增长率小于 0 |
| 上涨 | 环比方向为上涨，且增长率大于 0 且小于 999.99% |
| 持平 | 平台明确返回持平或增长率为 0 |
| 999.99%+ | 原始环比值通过单位校验且明确超过 999.99% |
| 增速快 | 平台明确返回“增速快”业务状态 |
| 无法确认 | 平台明确返回无数据或无法提供近1天指标 |
| 失败 | 重试后仍缺字段、错位、单位异常或接口异常 |

不能仅因为接口返回一个极大数就分类为 `999.99%+`。分类前至少校验：

- `pay_amount` 是有效数值或平台明确的有效档位；
- `pay_amount_range` 与数值所属档位一致；
- `pay_amount_hb` 的单位符合接口约定；
- 增长方向、增长率和今日成交数据互相不矛盾；
- 指标结果确实对应当前 `clue_id`。

当前发现的“无法确认”和 `999.99%+` 异常，必须优先按采集错误排查，不能直接作为正常业务结果接受。

### 6.4 昨日成交反推

普通上涨或下跌：

```text
昨日成交 = 今日成交精确值 ÷ (1 + 环比变化率)
```

然后将结果映射为平台金额档位。

特殊情况：

- 持平：昨日成交使用今日成交档位；
- 增速快：昨日成交填写 `-`；
- `999.99%+`：只有原始值和单位校验通过后，填写“小于”对应区间；
- 无法确认：今日、昨日、增长均填写 `-`；
- 失败：不进入成功数据表，只进入失败记录。

## 7. 重试、检查点和停止

### 7.1 重试

- 指标请求单商品最多重试 3 次；
- 等待时间按 3 秒、5 秒、8 秒递增；
- 列表接口失败也必须重试，但不能重复推进页码；
- 连续多页失败时暂停任务，保留检查点并提示用户检查登录态或限流；
- 字段解析异常与 HTTP 异常一样记录，不得静默吞掉。

### 7.2 检查点

检查点至少包括：

- 任务编号、创建时间、更新时间；
- 完整类目路径和类目 ID；
- 最低成交金额和采集口径；
- 当前页、下一页、总页数；
- 已处理商品和成功分类统计；
- 每条商品的原始列表数据、指标原始数据和解析结果；
- 失败商品、阶段、原因和重试次数；
- 最后一次页面/接口响应指纹。

检查点采用临时文件写入后原子替换，避免中断留下半个 JSON。继续任务时必须校验类目、阈值和采集口径一致。

### 7.3 停止

- 用户停止时，在安全边界完成当前商品后停止；
- 生成独立的部分报告；
- 部分报告不能覆盖上一份完整报告；
- “已处理数据完整”不等于“整个金额区间已覆盖”，两者必须分开记录。

## 8. 报告输出

每次任务生成同一任务编号对应的 Markdown、JSON 和 Excel 文件。

### 8.1 Excel 工作表

#### `采集汇总`

包含任务名称、任务编号、采集时间、采集状态、区间覆盖、类目路径、最低金额、达标商品数、增长结果数、各分类数量、失败数量和耗时。

#### `全部数据`

包含所有达到最低金额且完成指标校验的商品：

```text
# | 类目 | 产品名称 | 近30天总成交 | 昨日成交 | 今日成交 | 较昨日增长 | 分类
```

#### `成交增长`

保持参考 Excel 的 7 列结构：

```text
# | 类目 | 产品名称 | 近30天总成交 | 昨日成交 | 今日成交 | 较昨日增长
```

只包含上涨、`999.99%+`、增速快等正向增长结果。

#### `失败记录`

包含：

```text
类目 | 页码 | 产品名称 | 阶段 | 原因 | 重试次数
```

### 8.2 文件命名

```text
选品报告-成交增长-YYYYMMDD-HHmmss.xlsx
选品报告-成交增长-YYYYMMDD-HHmmss.md
选品报告-成交增长-YYYYMMDD-HHmmss.json
```

完整报告与部分报告使用不同文件名，不能互相覆盖。

## 9. 后端任务接口建议

```text
GET  /api/categories
POST /api/tasks
GET  /api/tasks
GET  /api/tasks/:taskId
POST /api/tasks/:taskId/pause
POST /api/tasks/:taskId/resume
POST /api/tasks/:taskId/stop
POST /api/tasks/:taskId/retry
GET  /api/tasks/:taskId/download?type=md|xlsx|json
```

创建任务的核心参数：

```json
{
  "category": {
    "displayPath": "传统滋补 / 药食同源食品 / 茯苓",
    "segments": ["传统滋补", "药食同源食品", "茯苓"],
    "valuePath": ["1000002718", "1000002731", "..."]
  },
  "minAmount": 10000
}
```

服务端必须重新校验类目对象来自最近一次类目发现结果，拒绝空类目、重复类目、伪造路径和过期路径。

## 10. 测试和验收

### 10.1 单元和模拟测试

- 金额档位解析、边界和空值；
- 环比小数与百分比单位转换；
- 上涨、下跌、持平、增速快、`999.99%+`、无法确认和失败分类；
- 指标响应错位、缺字段、非 JSON、超时和 HTTP 错误；
- 昨日成交反推和档位映射；
- 检查点恢复、去重和部分报告；
- Excel 四个 Sheet 的字段、顺序和统计守恒。

### 10.2 两种认证路线小样本对比

同一类目、同一最低金额、同一页数分别执行 Edge 页面上下文 API 和 `cookie.txt` 直连 API，至少记录：

- HTTP 状态和登录状态；
- 列表和指标完整率；
- 字段缺失率；
- 错位、重复和异常环比数量；
- `999.99%+` 和无法确认比例；
- 采集耗时；
- 是否出现验证、限流或异常退出。

小样本稳定前不得执行全量采集。

### 10.3 真实采集验收

- 单类目和最低金额可正确保存并恢复；
- 采集顺序按近30天成交降序；
- 所有达标且校验通过的商品进入全部数据；
- 分类数量与全部数据数量守恒；
- API 采集错误不会伪装成无法确认或 `999.99%+`；
- 失败商品均进入失败记录；
- 完整报告和部分报告互不覆盖；
- Excel 完成值检查、错误扫描和视觉检查后再交付。

## 11. 当前方案边界

- 本项目暂不实现上级项目的多类目批量任务；
- 本项目暂不依赖逐商品详情抽屉采集；
- 本项目不承诺规避平台风控；
- 真实大规模采集必须在小样本验证通过后由用户明确启动；
- API 返回结构改变时，先保存原始响应并更新解析 fixture，再修改分类逻辑。
