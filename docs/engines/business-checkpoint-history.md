# 故障记录：检查点 `WinError 5` 拒绝访问

## 结论

本次失败不是抖店平台风控。故障发生在本地 Windows 文件系统：采集线程写入检查点临时文件后，调用 `os.replace()` 替换正式 JSON 时，与网页状态/历史记录对同一检查点的读取发生竞争，Windows 返回 `WinError 5: 拒绝访问`。

6 并发和 30 秒页间等待不是这次错误的直接原因。它们影响平台请求节奏，但不能解决本地检查点文件锁竞争。

当前状态：已完成根因调查、P0 代码修复和离线压力验证；真实 UI 冒烟及 30 页以上长任务验收尚未执行。

## 修复进展（2026-08-28）

已实施：

- `/api/status` 只读取保存边界发布的独立内存快照；
- `/api/history` 使用启动缓存，并在任务结束时更新；
- 检查点读写共用进程内 `RLock`；
- 原子替换对 Windows 访问冲突执行 50～1600 ms 有限退避；
- 所有原子写入阶段的 `OSError` 统一分类，检查点错误与报告错误分别展示；
- 重试耗尽后任务进入检查点暂停，用户释放占用并点击继续后重新保存；
- 停止期间不会再次启动保存重试，最终报告生成、状态发布和事件清理彼此隔离；
- 服务启动时校验正式检查点；正式文件有效则清理旧临时文件，正式文件缺失或损坏则恢复最新有效临时文件；

## 证据

### 1. 错误位置属于本地磁盘，不属于平台 API

失败调用是：

```python
temporary.write_text(...)
os.replace(temporary, path)
```

临时文件已经完整写出，失败发生在临时文件替换正式检查点时。错误中没有 HTTP 状态码、登录失效、验证页、限流或接口响应异常。

本项目对真正的平台风险信号已有单独识别：HTTP 401、403、429、非 JSON 验证页等会产生不同错误。本次日志没有出现这些信号。

### 2. 文件权限正常

截图对应的正式检查点：

```text
data/checkpoints/api-1000000724-1000000728-2500000.json
```

检查结果：

- 大小：5,633,704 字节
- 属性：Archive
- `IsReadOnly = False`
- 当前用户及沙箱用户均有 Modify 权限
- 同目录成功存在正式 JSON 和失败遗留的 `.tmp`

这排除了“目录不可写”“文件只读”和固定 ACL 拒绝。

### 3. 文件在页数增加后快速变大

当前检查点同时保存：

- 每个结果的标准字段；
- 每个结果的 `raw_list`；
- 每个结果的 `raw_indicator`；
- 每一页完整的 `raw_list_response`；
- 分页检查点和任务统计。

到第 16 页、300 条成功结果时，单个检查点已达到约 5.6 MB。每次保存都会重新序列化整个对象、写出完整临时文件，再替换正式文件。

文件越大，完整读取和完整写入耗时越长，读写时间窗口重叠的概率越高，因此表现为前几页正常、十几页后更容易失败，而不是固定在某一页触发。

### 4. 网页在高频读取同一文件

当前数据流：

```text
浏览器每 1 秒请求 /api/status
        ↓
web_app.py 读取并解析完整检查点 JSON

浏览器每 12 秒请求 /api/history
        ↓
web_app.py 遍历并解析全部 api-*.json

采集线程每完成一个指标批次和每完成一页
        ↓
collect.py 写完整临时文件并 os.replace() 正式检查点
```

6 并发时，一页 18 条通常分成 3 个批次，因此一页至少会发生多次完整检查点替换。网页状态轮询和历史轮询会同时增加正式文件被打开的机会。

### 5. 已隔离复现

使用本次 5.6 MB 检查点复制到系统临时目录，不访问平台，只运行当前 `atomic_write_json()` 和并发 `read_text()`：

```text
测试时长：3.35 秒
原子写入尝试：30 次
成功读取：47 次
写入 PermissionError：10 次
读取 PermissionError：2 次
遗留 .tmp：10 个
```

在没有平台 API、没有登录态、没有网络请求的情况下仍可复现同类拒绝访问，根因由此确认是本地文件竞争。

## 根因链路

```text
检查点持续保存重复的原始响应
        ↓
文件增长到数 MB
        ↓
网页每秒读取 + 历史记录定时遍历
        ↓
采集线程频繁执行单次 os.replace()
        ↓
Windows 在目标文件被打开的瞬间拒绝替换
        ↓
没有锁、没有替换重试、没有 I/O 暂停状态
        ↓
任务被标记为 failed，并遗留 .tmp
```

## 数据影响

- 平台列表和指标请求在故障前是成功的；本次没有商品接口失败。
- 最终检查点保存了 300 条结果和前 16 页分页检查点。
- 第 17 页会在恢复时重新读取；已有 `processed_ids` 可用于跳过已保存商品。
- 已生成的报告是部分报告，不能视为阈值区间完整覆盖。
- 失败的临时文件不会被当前程序自动恢复或清理。

## 改正方案

### P0：先消除文件竞争（必须实施）

#### 1. 实时状态只读内存，不再每秒读检查点

- `TaskManager.state` 作为运行中任务的实时状态源。
- `/api/status` 在锁内复制精简公开状态，不读取磁盘 JSON。
- 磁盘检查点只用于进程重启恢复，不承担实时 UI 通信。
- `/api/history` 使用内存缓存；只在任务结束、手动刷新或服务启动时更新。

这项改动直接移除采集线程与网页轮询之间的同文件读写竞争。

#### 2. 给检查点读写增加同进程锁

- 检查点读取、临时文件替换和恢复操作共用一个 `RLock`。
- 所有代码路径通过统一的检查点存储组件访问文件。
- 锁只保护本地文件操作，不包住网络请求和 JSON 计算，避免阻塞采集。

#### 3. `os.replace()` 对短暂占用进行有限重试

- 临时文件只写一次。
- 替换遇到 `PermissionError` / `WinError 5` 时，使用短退避重试，例如 50、100、200、400、800、1600 ms。
- 替换成功后清理临时文件。
- 重试耗尽时进入“检查点保存暂停”状态，保留内存结果，不继续翻页；用户可重试保存或停止生成部分报告。
- 不能静默忽略保存失败，避免内存进度与磁盘进度分叉。

同进程锁解决程序自身竞争，有限重试负责杀毒软件、索引器等短暂外部占用。

#### 4. 正确区分错误类型

界面和日志分别显示：

- 本地检查点写入冲突；
- 平台限流（HTTP 429）；
- 登录失效（401/403 或登录页）；
- 平台验证页/非 JSON；
- 普通接口或数据校验失败。

本地 I/O 错误不能再显示成笼统的“任务失败”，避免误判为风控。

### P1：缩小检查点并降低重写成本（强烈建议）

#### 1. 拆分“运行状态”和“原始审计数据”

建议目录：

```text
data/tasks/<task_id>/state.json             # 小型任务状态，可原子替换
data/tasks/<task_id>/results.jsonl          # 标准结果，按批次追加
data/tasks/<task_id>/failures.jsonl         # 失败记录，按批次追加
data/tasks/<task_id>/raw/page-0001.json.gz  # 每页原始列表响应，写一次不再改
data/tasks/<task_id>/raw/indicator-*.json.gz
```

- `state.json` 只保存页码、统计、已处理 ID、文件位置和恢复游标。
- 原始响应不再重复嵌入每次重写的状态文件。
- 原始文件按页或批次写一次，可压缩保存，继续满足审计需要。
- 报告生成时流式读取结果文件，不依赖一个不断膨胀的巨型 JSON。

#### 2. 保存策略

- 每个指标批次追加一次结果日志，并更新小型 `state.json`。
- 每页列表原始响应单独落盘一次。
- 每页完成后更新分页游标。
- 服务启动时从 `state.json + JSONL` 恢复。

这样页数增加不会让每次保存成本线性放大。

#### 3. 临时文件恢复和清理

- 启动时扫描同任务 `.tmp`。
- 正式文件有效时删除过期临时文件。
- 正式文件缺失或损坏时，校验并恢复最新有效临时文件。
- 记录恢复来源和时间，不静默覆盖。

### P2：平台请求保护（与本次故障分开处理）

本次不是风控，但 6 并发仍应增加合规的自适应保护：

- 默认并发建议从 6 调整为 4，允许用户手动选择 2/4/6。
- 只有普通超时或 5xx 才逐级降并发并退避。
- 出现 HTTP 429、401、403、验证页或平台明确拦截时立即暂停，不自动绕过验证。
- 页面显示平台返回的真实状态码和暂停原因。
- 页间等待可保留 30 秒，但它不能替代接口级限流检测。

这部分用于降低后续真正触发平台保护的概率，不能作为 `WinError 5` 的修复。

## 推荐实施顺序

1. 先写一个可稳定复现检查点竞争的自动测试。
2. 实施 P0：内存状态源、检查点锁、替换重试和错误分类。
3. 运行原 5.6 MB 检查点的并发压力测试。
4. 实施 P1：状态与原始数据拆分。
5. 跑 30 页以上的本地模拟和真实小流量长任务。
6. 最后增加 P2 的平台状态自适应策略。

## 验收标准

- 5～10 MB 状态数据下，连续 100 次保存并同时刷新页面，不出现 `WinError 5`。
- 压力测试结束后没有遗留 `.tmp`。
- 运行中 `/api/status` 对检查点文件的读取次数为 0。
- 强制占用目标文件时，界面显示“检查点保存暂停”，释放后可继续，不丢失内存结果。
- 服务重启后可以从已提交的批次和页游标继续，不重复写入结果。
- 30 页长任务中检查点体积保持稳定或缓慢增长，不再每次重写全部原始响应。
- HTTP 429/401/403/验证页与本地 I/O 错误在日志和界面中明确区分。

## 当前建议

在代码修复前，不建议继续跑长任务。降低并发或增加页间等待不能可靠避免该本地文件竞争；最多只会改变碰撞概率。现有失败任务的 300 条结果和前 16 页进度仍在正式检查点中，应保留该文件，待恢复逻辑修复后继续。
