# 人工视频工作台：双来源读取与可辨识待选列表

日期：2026-10-14。用户确认同时需要罗盘和抖音页面中的视频，自行勾选后提取链接、下载；修复商机中心“仅看近30天增长”复选框布局。

## 1. 已定位问题与边界

- 商机复选框复用了普通输入字段布局，继承宽100%的规则，文字和勾选框分行且勾选框远离文字。仅为这个布尔字段使用同行布局，保留参数only30dGrowth含义。
- 人工读取目前只接受罗盘固定商品榜路径，页面选择器也排除了抖音标签；因此“当前页”并不是通用的视频读取。当前人工适配器没有first/up_and_first过滤，不能在没有真实页面证据时把用户观察直接归因于趋势条件。
- 罗盘卡片标题缺失时只显示相同商品名，现有UI缺少封面、商品分组、顺序、可用性和已选数量，用户无法判断具体视频。标题缺失不能伪装成已读取到视频标题。
- 支持受管Edge中正常打开的罗盘商品短视频榜，以及抖音视频详情、作者主页、搜索和推荐页面中已经加载并具有可识别视频ID的条目。只读当前已加载内容，不自动全站翻页，不改变罗盘趋势/类目。不能识别的页面明确提示，不把空结果或图文伪装成视频成功。

## 2. 界面方案

沿用现有深蓝文字、绿色操作和白色面板，使用frontend-design技能整理信息层次；不更换全局视觉风格。开源GUI的“先解析预览、筛选后勾选下载”流程可供参考：[douyin-downloader-gui](https://github.com/Mochasu123/douyin-downloader-gui)。只借鉴操作模式，不引入整个下载框架或手动复制Cookie流程。

```text
人工视频工作台
  打开罗盘 | 打开抖音 | 读取当前页
  粘贴分享链接/文案 → 添加

待选视频 98条                 已选 0条
  按标题/商品/作者筛选
  选择本页 | 清空选择 | 下载所选 | 复制链接/标题 | 导出 | 移除
  商品A / 店铺或来源
    [勾选] [封面] 第1条 真实标题或“标题未读取”   来源/视频ID/链接状态
    [勾选] [封面] 第2条 ...                    单条下载/复制链接
  商品B / ...
```

罗盘按商品分组；抖音按作者或页面来源分组。视频的编号只表示页面卡片顺序。显示真实标题、来源、商品/作者、视频ID及读取时间；未读到标题保留明确占位和封面，不重复把商品名称当作视频标题。没有公开链接时解释“下载时从平台读取”，不得一律显示“需重新读取”；临时播放地址只在内存，过期/页变动需重新读取。勾选后可批量操作，也可对单条操作。

封面使用从已打开页面读取的HTTPS图片地址，后端限制到已知平台图片CDN，CSP仅放行这些图片来源；不开放任意网页脚本/连接，不下载原视频作预览，也不新建视频备份。图片失效显示占位，可重新读取刷新。

## 3. 读取与数据设计

1. 罗盘继续复用独立snapshot/locate机制，所有已识别商品卡片进入候选，不调用自动视频趋势筛选。补齐卡片标题读取与商品/店铺、封面、序号、趋势展示信息。保留原卡片身份与页面变化校验，缺少唯一身份时不猜测下载别的视频。
2. 新增小型抖音页面读取模块：只接收www.douyin.com的HTTPS页面，读取可见DOM中/video/数字ID链接、当前视频详情及可识别modal_id。将相同视频ID去重，返回规范化公开链接、标题、封面、作者及来源。不依赖未公开签名接口，不读取Cookie明文，不更换用户页面。
3. 人工适配器按实际页面来源分派。抖音条目走现有公开链接下载能力；罗盘条目走现有会话定位与播放后下载。页面选择器展示来源名称和标题，加入“打开抖音”受管入口。
   罗盘另增“提取链接”短操作：选择具体条目后正常打开对应播放器取得播放地址和标题，结果仅在宿主内存保留临时播放地址。每批最多10条，共用原浏览器队列及120秒短操作上限；前端将较大选择分批提交，播放失败显示条目提示。复制链接优先公开链接，否则使用刚提取的播放链接。该操作不创建任务或视频文件。
4. 保留capture_items原有10列，新增以item_id为外键的capture_item_details扩展表，保存有限展示元数据JSON。旧待选记录仍可读取，不改任务/资产格式，不重置历史任务。新增表使用CREATE TABLE IF NOT EXISTS，原schema1保持兼容；旧版本忽略新表仍可读原表。
5. Capture.ingest校验字段类型、字符串长度、来源、封面地址及序号；同ID重复读取更新元数据，批量结果仍受200条及worker单消息1MiB限制。旧记录没有扩展信息时显示来源及稳定身份，不补造标题。
6. 列表支持分页、已选数量、本页选择和标题/商品/作者查询；保留最多200条一次下载。筛选、刷新和切页不应让用户看不见自己已选择的数量，删除后同步移除选择。

1. 写本文后实施：复选框和待选列表、展示元数据扩展、双来源读取及白名单打包登记。
2. 核对源码语法、异步读取路径、旧记录兼容、来源/封面校验、页面身份绑定和发布清单；合并前一次独立范围审查。不新增或运行自动化测试套件，真实页面只做定位所需最小读取；需要新的下载验收时另说明样本范围。
3. 完整修复提交后构建0.1.4，保留基础保护；安装包准备好后请用户退出，再升级原统一目录。安装前后核对数据指针和数据库，启动新版本；最后清理本次构建副本及旧包，记录实际边界，合并main、推送确认后删除开发分支。

## 5. 执行记录

初次只读检查发现DevToolsActivePort记录的端口已不再监听，专用浏览器未运行；用户随后打开真实罗盘和抖音页面。实际观察到罗盘短视频榜存在排名趋势为“-”的商品卡片，人工代码没有首次上榜过滤。抖音推荐页视频使用data-e2e-vid、video-desc和feed-video-nickname，可读取稳定视频ID、标题和作者。

快速只读候选检查取得罗盘132个可识别卡片（132个封面）及抖音2个已加载视频（2个标题/封面/公开链接）。罗盘标题位于悬停弹层，封面匹配逻辑在首卡真实检查可读取标题；正式人工读取为前200个缺标题卡片限制悬停次数和等待，超时保留明确占位，链接提取可继续补标题。下载和定位使用不逐条等标题的快照以避免不必要等待。

首条链接定位暴露原机制过严：所选商品与封面唯一匹配仍在，但其他商品“更多视频”展开加载使全页卡片清单哈希变化，旧snapshot定位拒绝下载。对具有唯一封面的条目改用包含页码、类目、榜单、品牌、商品清单的page身份，加上原商品和卡片唯一匹配；不再要求其他卡片集合完全相同。缺封面/原生ID的弱条目仍用原严格snapshot身份。翻页、筛选、商品清单或目标卡片变化继续拒绝；旧待选记录保留原身份，需重新读取。

上述修正后，对当前非首次上榜商品的一条视频正常打开播放器，resolve_items返回failed=0并取得播放地址；未创建下载任务或保存视频。标题悬停的正式读取在本次实际页面得到85个候选、40个已读标题，快速快照为132个候选，说明“更多视频”弹层加载会影响观测集合；数量按实际本次识别结果展示，不承诺所有隐藏视频已读取。

独立范围审查发现并修复两项身份边界：抖音URL/modal_id和播放器稳定ID冲突时拒绝补录，缺稳定ID时不借用播放器标题/封面；包含多条不同视频链接的父容器不复用同一展示元数据。罗盘批量提取每条都重新检查页码/筛选/商品清单，严格snapshot弱条目每次重新快照，再核对实际目标卡片。

实际候选的独立界面预览显示87条（2条抖音、85条罗盘），本页按作者/商品分组，8个当前加载封面正常显示；商机复选框与文字同排。预览使用只读展示数据和隔离浏览器，不等同于正式桌面桥接或下载验收。

用户选择“直接更新程序，我自己验收”，因此停止扩展验收范围，不执行新测试套件、旧库副本验收或两条下载样本。下一步直接构建安装；实际罗盘/抖音下载及作者主页、搜索、详情各种布局仍由用户现场验收，不能把当前推荐页识别和一次罗盘链接提取扩大为所有场景均验证。
