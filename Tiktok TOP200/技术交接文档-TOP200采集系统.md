## 1. 项目目标

为非技术用户提供一个可迁移的本地网页工具，从抖音电商罗盘的商品 TOP200 榜单中按条件批量采集数据。

用户可以选择：

- 一个或多个行业类目；
- 一种品牌类型；
- 一个或多个榜单类型。

系统依次处理每个“行业类目 × 榜单类型”组合，检查该榜单原始排名的前 200 名，只保存：

1. 带红色上升箭头的商品，例如 `↑ 1`；
2. 标记为“首次上榜”的商品。

下降、持平、无变化和无法确认趋势的商品不进入最终明细。

最终提供：

- 网页实时进度和历史结果；
- Excel 业务报表；
- JSON 结构化原始结果。

项目完成后，普通用户应能通过“安装一次依赖 → 双击启动 → 网页选择条件 → 登录抖店 → 开始采集 → 下载结果”完成全部操作。

## 2. 已确认的产品需求

### 2.1 行业类目

- 登录抖店后，从当前 TOP200 页面读取完整行业类目树。
- 网页界面支持搜索类目和多选类目。
- 一次任务可选择一个或多个类目，系统按队列依次处理。
- 类目路径必须保存完整层级文本，不能只保存末级名称。
- 若平台类目读取失败，应提示用户刷新或重试，不能静默使用错误类目。

### 2.2 品牌类型

品牌类型只提供三个选项，并且一次任务只能选择其中一个：

1. 不限；
2. 知名品牌；
3. 非知名品牌。

选择“不限”时，不再分别采集“知名品牌”和“非知名品牌”，避免重复数据。

### 2.3 榜单类型

- 登录后动态读取页面前六个业务榜单：总榜、搜索榜、直播榜、商品卡榜、达人带货榜、短视频榜。
- 按用户最终确认，不采集“实时爆品挖掘榜、退后购买榜、同行低退榜”。
- 用户可选择一个榜单，也可同时选择多个榜单。
- 选择一个时就是单榜采集；选择多个时按选择顺序依次采集。
- 页面新增或移除榜单时，应优先通过动态读取适配。
- 某个榜单因账号权限或类目限制不可用时，记录失败原因并继续其他组合。

### 2.4 时间范围

用户不需要手动选择时间范围，系统按以下规则自动决定：

1. 当前榜单支持“实时”时，采集实时数据；
2. 当前榜单不支持“实时”时，自动切换到“近1天”；
3. 结果必须同时记录期望周期和实际使用周期，不能让用户误以为所有榜单都是实时数据。

不采集近7天或近30天。

### 2.5 TOP200 与趋势过滤口径

- “TOP200”指平台榜单原始排名第 1 至第 200 名。
- 系统先检查原始 TOP200，再筛选上升和首次上榜。
- 不得为了凑够 200 条符合条件的数据继续扫描第 201 名以后。
- 最终结果可以少于 200 条。
- 若页面本身不足 200 条，应按实际数量结束并记录原因。
- 不得使用空数据、重复数据或其他类目的数据补足数量。

趋势识别规则：

| 页面状态 | 是否保存 | 结构化结果 |
|---|---:|---|
| `↑ 1`、`↑ 12` 等红色上升标识 | 是 | `trendType=up`，并保存上升名次 |
| `首次上榜` | 是 | `trendType=first`，上升名次为空 |
| 下降箭头 | 否 | 只计入排除统计 |
| 持平、横线或无变化 | 否 | 只计入排除统计 |
| 无法识别 | 否 | 计入解析异常统计并记录原因 |

## 3. 需要采集的数据

### 3.1 固定业务字段

每条符合条件的记录至少包含：

| 字段 | 含义 |
|---|---|
| 任务编号 | 本次批量任务的唯一标识 |
| 采集时间 | 实际读取该记录的时间 |
| 行业类目 | 完整类目路径 |
| 品牌类型 | 不限、知名品牌或非知名品牌 |
| 榜单类型 | 当前榜单名称 |
| 请求周期 | 默认期望的实时周期 |
| 实际周期 | 实时或近1天 |
| 当前排名 | 商品在当前榜单中的原始名次 |
| 趋势类型 | `up` 或 `first` |
| 趋势原文 | 例如 `↑ 1` 或 `首次上榜` |
| 上升名次 | 从红色箭头解析的整数；首次上榜时为空 |
| 商品名称 | 页面显示的完整商品名称 |
| 价格/价格带 | 页面显示的价格文字 |
| 商品链接 | 可回查的商品地址 |
| 店铺名称 | 页面显示的店铺名称 |
| 用户支付金额 | 保留页面原始区间文字 |
| 点击次数 | 保留页面原始区间文字 |
| 点击成交转化率 | 保留页面原始百分比区间 |
| 商品成交件数 | 保留页面原始区间文字 |
| 页面号 | 数据来自第几页 |
| 页内序号 | 当前页中的行序号 |

不保存商品图片或图片地址。

### 3.2 不同榜单的动态字段

不同榜单可能显示不同指标。除上述固定字段外，页面中其他可见业务列也必须保存。

实现时使用 `extraFields` 保存动态列：

```json
{
  "extraFields": {
    "页面列名": "页面原始显示值"
  }
}
```

“查看详情”“加入追踪”“找货源”等操作按钮不属于业务数据，不需要保存。

## 4. 技术架构

### 4.1 推荐技术栈

沿用 `商机中心` 已验证的技术方向：

- 操作系统：Windows；
- 运行时：Node.js 20 或更高版本；
- 浏览器自动化：`playwright-core`；
- 浏览器：用户电脑上的 Microsoft Edge；
- 浏览器连接：Chrome DevTools Protocol（CDP）；
- 本地服务：Node.js HTTP 服务；
- 操作界面：本地 HTML、CSS、JavaScript，不依赖外网 CDN；
- Excel 导出：`xlsx`；
- 结构化存储：JSON 文件；
- 实时日志：Server-Sent Events 或同等简单的单向推送方式。

### 4.2 系统数据流

```text
用户双击启动程序
  → 打开本地操作网页
  → 启动或连接调试版 Edge
  → 用户手动登录抖店
  → 读取类目树与榜单列表
  → 用户选择类目、品牌和榜单
  → 服务端建立组合任务队列
  → 采集器逐组合设置筛选条件
  → 实时优先，否则切换近1天
  → 翻页检查原始前200名
  → 保留上升和首次上榜
  → 每个组合写入检查点
  → 生成 JSON 与 Excel
  → 网页展示结果和下载入口
```

## 6. 采集执行流程

1. 启动本地服务并打开操作网页。
2. 检测 9222 端口是否已有可用的调试版 Edge。
3. 若没有，使用非默认用户数据目录启动真实 Edge。
4. 用户在 Edge 中手动登录抖店。
5. 采集器连接 CDP，并进入商品 TOP200 页面。
6. 读取完整行业类目和当前可用榜单。
7. 接收用户选择，建立“类目 × 榜单”任务队列；品牌类型对整批任务固定。
8. 对每个组合设置类目、品牌类型和榜单。
9. 检测当前榜单是否提供实时周期，按规则选择实时或近1天。
10. 确认页面刷新完成，并验证筛选条件和榜单状态。
11. 从第1页开始读取表头和数据行。
12. 解析当前排名、趋势、商品、店铺、核心指标、链接和动态列。
13. 只将上升和首次上榜写入结果；其他状态只增加统计数。
14. 翻页前记录活动页码和当前页商品指纹。
15. 翻页后确认页码或商品指纹变化，避免重复采集同一页。
16. 达到原始第200名、分页结束或页面实际数据结束时停止当前组合。
17. 写入组合检查点后继续下一个组合。
18. 全部组合结束后生成最终 JSON 和 Excel，并在网页显示结果。

不得仅依赖某个选择器出现就判断页面数据已更新。抖店 React 页面可能保留旧 DOM，应结合固定等待、页码、首行内容或页面指纹确认状态。

## 7. 任务恢复、重试与去重

### 7.1 检查点续跑

- 每完成一个“类目 × 榜单”组合就写入检查点。
- 检查点包含任务参数、已完成组合、当前组合、统计、临时结果和失败记录。
- 程序意外关闭后，网页应能发现未完成任务并让用户继续。
- 续跑时跳过已经完整完成的组合，不能重复采集。
- 用户明确选择“重新开始”时才创建新任务。

### 7.2 重试规则

- 页面加载、筛选切换和翻页失败采用有限次数重试。
- 每次重试重新定位当前 DOM，避免引用已经失效的元素。
- 重试次数耗尽后记录类目、榜单、周期、页码、操作阶段和错误原因。
- 单个组合失败不能阻止后续组合执行。
- 失败组合可从网页单独重试。
- 不允许无限重试。

### 7.3 去重规则

- 同一个类目、品牌、榜单和周期组合内，优先使用商品ID或规范化商品链接去重。
- 页面没有稳定ID或链接时，使用“商品名称 + 店铺名称”作为后备键。
- 同一商品出现在不同类目或不同榜单时保留多条记录，因为其排名和趋势上下文不同。
- 去重后仍需记录原始扫描数和重复数，便于核对完整性。

## 8. 输出文件

### 8.1 Excel

每次任务生成一个 Excel 文件，至少包含三个工作表：

1. `任务汇总`
   - 任务编号、开始/结束时间；
   - 选择的类目、品牌类型和榜单；
   - 每个组合实际使用的周期；
   - 扫描数量、上升数量、首次上榜数量、排除数量和失败数量。
2. `符合条件明细`
   - 所有上升和首次上榜记录；
   - 表头启用筛选；
   - 商品链接可点击；店铺仅显示名称；
   - 不插入商品图片。
3. `失败记录`
   - 失败组合、页码、阶段、错误原因和重试次数。

### 8.2 JSON

- JSON 是可复查、可续跑和便于二次处理的结构化结果。
- 保留任务参数、任务统计、符合条件明细、动态字段和失败记录。
- 最终 JSON 不需要保存所有被排除商品的完整详情，但必须保存各排除状态的数量。

### 8.3 文件命名

建议使用：

```text
reports/TOP200-YYYYMMDD-HHmmss-任务编号.xlsx
reports/TOP200-YYYYMMDD-HHmmss-任务编号.json
```

不得覆盖历史结果。

以下约束同时以 `抖店环境与采集约束.md` 为准：

7. 不绕过抖店访问限制、验证机制或反自动化措施。
8. 控制点击和翻页节奏，页面稳定后再读取。
9. 不要因追求速度牺牲分页和数据完整性验证。
10. 所有代码、配置、日志、检查点和结果使用项目内相对路径。

## 11. 测试方案

### 11.1 自动测试

至少覆盖：

- 识别单数和多位数上升名次；
- 识别首次上榜；
- 排除下降、持平、横线和空趋势；
- 无法识别趋势时生成解析异常；
- 实时可用时选择实时；
- 实时不可用时回退近1天；
- TOP200 截止边界；
- 页面不足200条；
- 翻页未变化和重复页检测；
- 组合内去重及跨榜单记录保留；
- 动态表头映射到 `extraFields`；
- 检查点恢复不会重复执行已完成组合；

## 14. 已知风险

- 抖店页面可能改版，DOM 类名和组件层级会变化。
- 不同榜单可能使用不同表头、分页大小或趋势展示方式。
- 账号权限可能导致部分榜单、类目或指标不可见。
- React 页面可能在旧 DOM 尚未移除时显示新页码，造成伪翻页。
- 批量组合较多时任务耗时较长，因此检查点续跑是必须能力。
- 页面显示的金额和数量通常是区间值，不能当作精确值处理。
- 平台数据本身可能少于200条，这不属于程序错误。

遇到页面差异时，应先保存证据、确认实际 DOM 和数据口径，再做最小范围修改。不要通过增加高频点击、绕过验证或迁移 Cookie 解决问题。
