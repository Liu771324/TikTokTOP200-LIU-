# 抖店环境与采集约束

本文档记录 `Tiktok TOP200` 项目必须遵守的抖店环境约束。这些约束继承自同级 `商机中心` 项目的实际采集经验，后续设计、开发、测试和运行均以此为基础。

## 一、浏览器与登录

1. 使用真实的 Microsoft Edge 浏览器运行抖店。
2. 采集程序通过 Chrome DevTools Protocol（CDP）连接远程调试模式下的 Edge。
3. Edge 必须使用非默认的用户数据目录启动远程调试，例如临时的 `edge-debug` 目录。
4. 保留用户手动登录抖店的环节，不尝试绕过登录、验证码或平台风控。
5. 不将抖店 Cookie 导入 Playwright 或其他自动化浏览器。
6. 不通过复制、解密或迁移 Edge 用户数据的方式复用登录状态。
7. 不使用 Playwright 自带 Chromium 模拟真实用户登录抖店。

## 二、采集行为

1. 所有自动化操作均在已登录的真实 Edge 会话中执行。
2. 控制点击、翻页和数据读取节奏，避免高频操作触发平台风控。
3. 页面刷新、筛选、排序或翻页后，必须等待页面数据稳定再提取。
4. 对偶发的页面加载和数据读取失败采用有限次数重试，不进行无限重试。
   - 当前页翻页同时校验页码和商品指纹，失败时重新定位 DOM，最多尝试 3 次。
   - 长时间采集发生页面卡顿时，当前“类目 × 榜单”组合从第 1 页自动重试，整组最多尝试 3 次；仍失败则记录原因并继续后续组合。
   - 重试不得刷新正在采集的页面，也不得高频点击。
5. 不尝试绕过抖店的访问限制、验证机制或反自动化措施。
6. 采集范围仅限用户有权访问的抖店页面和数据。

## 三、页面交互

1. 抖店页面使用的类目级联选择器、表格、固定列和分页组件可能需要针对实际 DOM 结构处理。
2. 类目选择不能假定普通点击一定有效；应参考 `商机中心` 已验证的 Cascader 交互经验。
3. 表格采集需要考虑固定列与横向滚动区域可能生成重复或分离的 DOM。
4. 排序状态不能只依赖一次点击，应校验列头状态或采集结果。
5. 翻页后必须验证页码或首行数据确实发生变化，避免重复采集同一页。
6. 抖店页面改版后，应先重新检查 DOM 和交互流程，再调整选择器。

## 四、数据质量

1. 每个品类的 TOP200 结果必须校验实际条数、去重结果和关键字段完整性。
2. 不得用空值、重复记录或上一品类的数据补足 200 条。
3. 若某品类实际可用数据不足 200 条，应如实记录实际数量和原因。
4. 采集结果应保留品类、采集时间、排序口径和数据来源等必要元信息。
5. 采集异常应明确记录，不静默忽略可能影响结果完整性的错误。
6. 商品链接必须写入 JSON 和 Excel 的“商品链接”列；Excel 单元格必须可点击。
7. “当前排名”必须保存平台原始 TOP200 名次，不能按过滤后的结果重新编号。
8. 店铺入口为二维码，只保存店铺名称，不采集二维码或店铺链接。

## 五、项目边界

1. `Tiktok TOP200` 是独立项目，代码、配置、日志和输出均放在本目录内。
2. `商机中心` 仅作为抖店环境、技术方案和踩坑经验的参考，不直接修改其文件。
3. 不复制 `商机中心` 中已经确认不可用或容易触发风控的方案。
4. 新增依赖和运行方式应在本项目文档中单独说明。

## 六、变更原则

如后续项目文档、页面实测结果或用户要求与本文档存在冲突，应先确认并更新本文档，再实施相关代码变更。
