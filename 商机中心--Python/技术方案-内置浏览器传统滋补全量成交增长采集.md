# 内置浏览器采集“传统滋补”成交增长数据技术方案

> 日期：2026-08-13  
> 状态：历史参考方案，已由《技术方案-API单类目全量分类采集》替代  
> 执行方式：历史基线为内置浏览器逐页操作；当前项目不再以逐商品详情抽屉为正式采集路径，改为单类目 API 采集  
> Excel 模板：`D:/前端/ai/Script All/商机中心/选品报告-成交增长.xlsx`

## 一、目标

在抖店商机中心选择父类目“传统滋补”，按近30天成交金额降序读取全部符合条件的数据，筛选近30天成交金额展示档位下限不低于 ¥10,000 且今日成交高于昨日的商品，生成与参考模板结构一致的 Excel。

最终文件名：`传统滋补-成交增长-YYYYMMDD-HHMMSS.xlsx`。

## 二、数据口径

- 品类：传统滋补父类目。
- 排序：近30天成交金额降序。
- 金额条件：展示档位下限不低于 ¥10,000。
- 增长条件：今日成交高于昨日成交。
- 普通上涨：使用近1天成交金额和较上周期增长率反推昨日成交区间。
- “增速快”：保留，昨日成交填写 `-`。
- `999.99%+`：增长显示为 `>999.99%`，昨日成交显示对应“小于”区间。
- 下跌、持平和无法确认上涨的商品不进入主表，但计入分类统计。

## 三、Excel结构

工作表固定为“成交增长”：

1. 第1行：采集时间。
2. 第2行：品类“传统滋补”。
3. 第3行：筛选口径。
4. 第4行：达标、增长、下跌、持平、失败、重试和完整性统计。
5. 第5行：空行。
6. 第6行及以后：`#`、产品名称、近30天总成交、昨日成交、今日成交、较昨日增长。
7. 三次失败的商品追加到“以下为未完成采集”区，记录页码、尝试次数和失败原因。

## 四、内置浏览器执行流程

1. 打开商机中心；登录、扫码、验证码和风控验证由用户亲自处理。
2. 选择父类目“传统滋补”，切换列表视图。
3. 按成交金额降序，并用页面头尾金额确认排序。
4. 对金额达标商品逐个打开详情，切换“近1天”，读取今日成交、增幅和涨跌方向。
5. 单商品最多重试3次，等待3秒、5秒、8秒；失败后记录并继续。
6. 每页处理完后关闭抽屉、保存检查点、固定等待40秒，再翻页并验证页码与内容指纹变化。
7. 最后一页或进入低于金额阈值的数据区域后停止，不再额外等待40秒。

## 五、检查点与续跑

每页保存 `checkpoints/传统滋补-成交增长-YYYYMMDD-HHMMSS.json`，包含采集日期、筛选条件、已完成和下一页页码、总页数、分类统计、累计结果、失败记录、页面指纹与最后更新时间。

只允许同一天、同品类、同筛选口径且页面指纹相符时续跑；以“产品名称 + 近30天总成交”去重。遇到登录失效、验证码、风控或中断时先保存检查点，再等待用户处理。

## 六、验收标准

- Excel与参考模板保持相同工作表、顶部4行元数据、空行、六列表头和失败区结构。
- 每次翻页前已保存检查点并完整等待40秒。
- 抽查首、中、末页排序及指纹，抽查至少5个入选商品详情与反推结果。
- 覆盖普通上涨、增速快、`999.99%+`、下跌、持平和三次失败场景。
- 分类总数满足完整性守恒，失败商品不静默丢失。
- Excel完成数值检查、错误扫描和视觉渲染后交付。

## 七、安全边界

40秒间隔只用于降低操作频率，不承诺规避平台风控。不得绕过验证码、安全验证或登录机制；出现验证时由用户亲自完成。
