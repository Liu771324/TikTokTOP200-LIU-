# 抖店商机中心数据采集操作文档

> 最后更新：2026-08-28
>
> 文档定位：当前项目的 API 单类目采集操作说明
>
> 当前正式方案：见《技术方案-API单类目全量分类采集》
>
> 当前状态：只更新文档；本阶段不修改程序、不修改现有结果文件、不启动采集

本项目是上级“商机中心”的单类目 API 换代升级版。一次任务只采集一个类目节点；用户在前端选择类目和最低成交金额；达到阈值且完成校验的数据全部保留，并按参考 Excel 的业务口径输出。

---

## 一、操作路径

### 1. 入口

- 网址： https://fxg.jinritemai.com/ffa/bu/NewBusinessCenter?clueChannel=all_word
- 路径：抖店后台 → 商品 → 商机中心 → 追抖音热词
- 正式使用：登录 Edge 后打开前端任务页面，由前端创建采集任务。

### 2. 登录和认证

默认认证路线是 Edge 页面上下文中的 API 调用：

- 复用当前已登录的 Cookie、来源页、User-Agent 和浏览器网络环境；
- API 负责高速读取，浏览器主要承担登录态和页面上下文；
- 不承诺完全不触发平台限流或风控。

cookie.txt 直连 API 只保留为独立备用实验路线：

- 不与 Edge 路线混合采集同一个任务；
- 先用同类目、同阈值、1～3 页小样本对比；
- Cookie 过期、返回登录页、401、403 或连续异常时立即停止；
- Cookie 不得写入日志、报告、检查点或前端返回值。

### 3. 前端任务设置

前端需要提供：

1. 类目树读取、搜索和选择；
2. 选中节点的完整类目路径展示；
3. 最低成交金额输入；
4. 创建、暂停、继续、停止和重试任务；
5. 查看页码、已采集数量、分类统计和失败数量；
6. 下载 Excel、Markdown、JSON 报告。

最低成交金额由用户配置，不再固定为 ≥75万。选择父类目时，任务包含该节点及其子类目；任务必须保存类目名称、节点 ID、层级和完整路径，避免重名类目采集错误。

## 二、已验证的核心 API

### 1. 列表接口

POST /api/commop/business_chance_center/clue/common/real_time_list

基础请求体：

```json
{
  "condition": {
    "categories": [{"first_cid": 1000002718}],
    "hit_clue_label_ext": true,
    "show_new_supply_link": true,
    "include_hot_sales_products": true,
    "sort": {"sort_direction": 1, "sort_field": "TRADING_AMOUNT"}
  },
  "clue_type": "",
  "clue_type_new": 11,
  "page": {"current": 1, "page_size": 18},
  "terminal_type": 0,
  "source": "business_center"
}
```

关键约定：

- sort_field 为 TRADING_AMOUNT，按近 30 天成交金额排序；
- page.current 从 1 开始，page.page_size 默认 18；
- 类目参数必须来自前端当前选择的类目对象；
- 读取列表后，必须保存原始响应和解析结果；
- 不能只保存类目名称，必须保存节点 ID 和完整路径。

常用字段：

- clue_detail.clue_id
- clue_detail.name
- clue_detail.category_path
- clue_indicator.pay_amount_ind
- clue_indicator.pay_amount_ind_range

### 2. 指标接口

POST /api/commop/business_chance_center/clue/common/indicator

请求体：

```json
{
  "clue_id": 67803642,
  "recently_day_type": 1
}
```

请求头需要按真实页面请求保留 Content-Type 和 agw-js-conv: str。recently_day_type=1 表示近 1 天口径。

常用字段：

- data.pay_amount
- data.pay_amount_hb
- data.pay_amount_range
- data.search_pv_cnt
- data.demand_supply_rate
- data.online_prod_cnt

指标响应必须按 clue_id 绑定回商品，不得按并发请求返回顺序盲目写回。

### 3. 类目接口

类目树优先从商机中心类目接口读取：

GET 或 POST /api/commop/business_chance_center/shop_full_category/list

实际请求方法、参数和子类目字段以已登录页面产生的真实请求为准。开发时应先保存脱敏响应 fixture，再实现父类目、子类目和完整路径映射，不能仅凭字段名称猜测。

## 三、当前正式采集流程

### 1. 创建任务

1. Edge 登录抖店并确认商机中心页面可正常访问。
2. 前端读取类目树，用户选择一个节点。
3. 前端显示完整类目路径和节点 ID。
4. 用户输入最低成交金额。
5. 后端保存任务快照：任务编号、类目路径、类目 ID、阈值、认证路线、创建时间和采集口径。
6. 任务进入待运行状态。

### 2. 采集一页

1. 调用 real_time_list 获取当前页。
2. 校验响应是 JSON，页码正确，商品 ID 不为空，成交金额字段可解析。
3. 对本页商品调用 indicator，默认每批最多 6 个并发。
4. 按 clue_id 写回指标结果。
5. 校验今日成交、金额档位、环比值和响应归属。
6. 将原始响应、解析结果、失败原因和重试次数写入检查点。
7. 默认等待约 20 秒后再访问下一页。

### 3. 停止条件

列表必须按近 30 天成交金额降序读取。当前页全部商品均确认低于用户设置的最低金额，并且排序和金额解析通过校验后，才可停止继续翻页。

以下情况不得直接停止：

- 金额档位无法解析；
- 页内存在空值或异常值；
- 列表排序无法确认；
- 指标接口失败；
- 响应错位或单位异常。

历史试采中的 56 页、1003 条、≥75万只是历史数据，不是固定页数、条数或业务阈值。

### 4. 小样本验证脚本的定位

浏览器 Console 中的 fetch 脚本只用于 1～3 页的接口字段验证、认证路线对比和异常复现，不是正式生产入口。正式入口应是前端任务页面 + 后端任务系统。

## 四、数据清洗、分类和异常

### 1. 金额和字段清洗

- 保留平台原始金额档位文本；
- 最低金额判断使用可验证的档位下限；
- 无法解析的金额不得静默转换成 0；
- 指标结果必须与请求的 clue_id 对应；
- 字段缺失、响应错位、非 JSON、超时、单位异常或数值矛盾，重试后进入失败记录。

### 2. 分类规则

| 分类 | 条件 |
|---|---|
| 下跌 | 环比方向为下跌，且原始环比值小于 0 |
| 上涨 | 原始环比值大于 0，且小于 999.99% |
| 持平 | 平台明确返回持平或原始环比值为 0 |
| 999.99%+ | 原始环比值通过单位和一致性校验后超过 999.99% |
| 增速快 | 平台明确返回“增速快”业务状态 |
| 无法确认 | 平台明确返回无数据或无法提供近 1 天指标 |
| 失败 | 重试后仍缺字段、错位、单位异常或接口异常 |

999.99%+ 不能因为单个异常大数直接生成。至少需要同时校验原始环比值、今日成交值、金额档位、单位和增长方向。当前已复查发现的异常结果，优先按采集错误排查，不得把采集错误伪装成无法确认或 999.99%+。

### 3. 昨日成交

普通上涨或下跌使用：

昨日成交 = 今日成交精确值 ÷ (1 + 环比变化率)

然后将结果映射为平台金额档位。

- 持平：昨日成交使用今日成交档位；
- 增速快：昨日成交填写 -；
- 999.99%+：校验通过后按平台规则填写；
- 无法确认：相关指标填写 -；
- 失败：不进入成功数据。

## 五、节奏、重试和检查点

### 1. 默认节奏

- 页间等待约 20 秒；
- indicator 每批并发不超过 6；
- 参数可以配置，但默认不使用激进提速；
- 遇到 401、403、429、登录页、验证页或异常空响应，立即暂停任务。

### 2. 重试

- 单个指标请求最多重试 3 次；
- 建议等待 3 秒、5 秒、8 秒递增；
- 列表失败不得推进页码；
- 连续多页失败时暂停并保留检查点；
- 解析错误和 HTTP 错误一样记录，不能静默吞掉。

### 3. 检查点

每个检查点至少保存：

- 任务编号、更新时间、完整类目路径、类目 ID 和最低金额；
- 当前页、下一页和区间覆盖状态；
- 每条商品的原始列表响应、指标原始响应和解析结果；
- 成功分类统计；
- 失败记录、采集阶段、失败原因和重试次数。

检查点必须采用临时文件写入后原子替换。恢复任务前校验类目、阈值、认证路线和采集口径一致。

## 六、最终 Excel 结构

最终 Excel 固定为四个工作表，字段口径参考上级“商机中心”结果。

### 1. 采集汇总

包含：

- 任务名称、任务编号、采集时间、采集状态；
- 类目、阈值、区间覆盖；
- 达标数量、各分类数量、增长数量、失败数量、耗时。

### 2. 全部数据

固定 8 列：

#、类目、产品名称、近30天总成交、昨日成交、今日成交、较昨日增长、分类

只放达到最低金额且指标校验通过的数据。

### 3. 成交增长

保持参考 Excel 的 7 列结构：

#、类目、产品名称、近30天总成交、昨日成交、今日成交、较昨日增长

只放上涨、999.99%+、增速快等正向增长结果。

### 4. 失败记录

固定 6 列：

类目、页码、产品名称、采集阶段、失败原因、重试次数

失败记录不能混入全部数据，也不能被改写成无法确认。

## 七、报告文件和验收

每个任务生成同一任务编号对应的 Excel、Markdown 和 JSON 文件。完整报告和部分报告使用不同文件名，不能互相覆盖。

后续实现必须完成：

- 单类目选择和最低金额配置；
- API 分页、指标采集和断点续跑；
- 正常增长、下跌、持平、999.99%+、增速快、无法确认和失败的明确处理；
- 两种认证路线同类目、同阈值、1～3 页小样本对比；
- API 模拟、分类、异常、检查点恢复和 Excel 结构测试；
- 小范围真实采集验收通过后，才允许执行全量任务。

本阶段不修改程序、不修改现有结果 Excel、不修改现有检查点、不启动任何采集任务。
