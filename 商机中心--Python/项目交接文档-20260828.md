## 2. 项目定位

这是抖店商机中心的单类目 API 采集工具。一次任务选择一个一级、二级或三级类目范围，根据近 30 天成交金额阈值向下翻页，为达标商品读取近 1 天成交指标，完成分类后生成报告。

当前架构不是 Node 后端，也不是 AI 实时点击页面：

```text
用户浏览器
  │  http://127.0.0.1:8765
  ▼
public/index.html
  │  本地 JSON API
  ▼
web_app.py（Python HTTPServer + 后台采集线程）
  │
  ├─ Edge CDP 9222：读取登录态和官方类目树
  ├─ requests：调用列表/指标 API
  ├─ data/checkpoints：任务检查点
  └─ reports/<task_id>：Excel / Markdown / JSON
```

Edge 主要提供已登录会话和类目接口所需的页面签名 URL。正式列表和指标数据由 Python `requests` 读取。

## 7. 类目发现与三级联动

### 7.1 官方类目接口

类目入口：

```text
/api/commop/business_chance_center/shop_full_category/list
```

该接口带页面生成的 `verifyFp`、`msToken`、`a_bogus` 等签名查询参数。代码没有自行生成或绕过签名，而是：

1. 连接已登录 Edge；
2. 在商机中心页面的 Performance Resource 记录中寻找已加载的完整签名 URL；
3. 使用同一 Playwright 浏览器上下文的 `context.request.get()` 读取；
4. 只解析前三层 `{value, label, children}`；
5. 返回精简的 `{id, name, children}` 给本地前端。

类目树缓存在 `TaskManager.categories_cache`。当前真实环境读取到 47 个一级类目；传统滋补读取到 12 个二级类目。

## 8. 采集数据流

### 8.1 平台接口

列表：

```text
POST /api/commop/business_chance_center/clue/common/real_time_list
```

固定口径：

- `clue_type_new = 11`；
- `page_size = 18`；
- `sort_field = TRADING_AMOUNT`；
- `sort_direction = 1`；
- 类目对象包含实际选择到的一级至三级 ID。

指标：

```text
POST /api/commop/business_chance_center/clue/common/indicator
agw-js-conv: str
```

固定参数：`recently_day_type = 1`。

### 8.2 每页流程

```text
读取列表页
  ↓
校验 JSON、商品 ID、金额精确值和金额档位
  ↓
校验页内按近 30 天成交金额降序
  ↓
按金额档位下限筛选达标商品
  ↓
按 batch_size 并发读取指标
  ↓
按 clue_id 绑定、校验并分类
  ↓
每批保存检查点
  ↓
每页追加原始列表响应并再次保存
  ↓
满足停止条件或等待下一页
```

### 8.3 停止条件

以下任一条件结束：

- 列表为空；
- 返回商品少于 18；
- 当前整页所有商品的金额档位下限都低于阈值；
- 达到 `max_pages` 小样本页数；
- 用户停止；
- 登录、限流或验证等立即停止错误。

不能因为当前页出现一条低于阈值的商品就停止。代码会检查整页，并校验跨页金额不能回升。

### 8.4 重试、暂停和停止

- 列表、指标和解析错误共用 3 次重试；
- 重试间隔：3、5、8 秒；
- 暂停由全局 `PAUSE_EVENT` 控制，在当前最多 6 个指标的批次结束后生效；
- 暂停期间重试等待和页间等待也会冻结；
- 停止由 `STOP_EVENT` 控制，完成安全边界后保存检查点和部分报告。

## 9. 校验与分类

### 9.1 金额校验

列表与指标同时保留精确数值和平台金额档位。精确值必须落在对应档位内，否则该响应失败，不静默修正。

阈值判断使用金额档位下限。例如阈值为 750,000 元时，只有档位下限大于或等于 750,000 的商品进入指标采集。

### 9.2 分类

成功数据只有六类：

| 分类 | 当前判断 |
|---|---|
| 下跌 | 原始环比小于 0 |
| 上涨 | 原始环比大于 0 且小于 9.9999 |
| 持平 | 环比等于 0 或平台明确持平 |
| 999.99%+ | 原始环比大于或等于 9.9999 且通过一致性校验 |
| 增速快 | 平台状态或标签明确包含“增速快” |
| 无法确认 | 平台明确无数据、暂无数据或无法提供 |

重试后仍缺字段、金额矛盾、`clue_id` 错位、环比单位异常或方向矛盾的商品进入失败记录，不混入六类成功数据。

普通上涨/下跌的昨日成交：

```text
昨日精确值 = 今日成交精确值 / (1 + 原始环比)
```

结果映射回平台金额档位。

## 13. 已知问题和限制

### P0：Windows 检查点文件竞争

状态：已确认、已复现、P0 已修复并通过离线测试；真实 UI 和 30 页以上长任务待验收。

证据：5.6 MB 状态下，30 次并发写入出现 10 次写拒绝、2 次读拒绝、10 个遗留临时文件。完整分析见故障记录。

影响：长任务通常在文件增大后失败；降低并发或增加页间等待只能改变碰撞概率，不能修复。

### UI 固定新建任务

前端启动参数固定 `fresh: true`。同一类目/阈值再次开始会创建新任务并覆盖正式检查点路径，不会从旧页码继续。CLI 省略 `--fresh` 才支持当前检查点续跑。

在增加明确的“新建/继续”选择前，不要让用户用网页尝试恢复截图中的第 17 页。

### 历史记录不是任务管理器

历史记录只显示最近 5 个摘要。不能点击切换任务，不能从历史卡片下载报告，重启服务后 `/api/download` 没有当前任务上下文。

### 报告路径可能失效

检查点保存绝对路径，但报告目录可能被移动或删除。当前 API 只在下载时检查文件是否存在；历史列表不显示失效状态。

### 类目树依赖页面资源记录

如果 Edge 商机中心页面没有加载类目接口，代码会刷新页面后再找签名 URL。平台修改前端加载方式、接口路径或响应字段时，`/api/categories` 会失败。

### 认证缓存没有主动刷新

Cookie 在服务进程内缓存。服务运行期间 Cookie 过期后，当前实现不会在下一任务开始前主动刷新；平台返回 401/403/非 JSON 时任务停止。

### 单线程 HTTP 服务不要随意改回线程版

`web_app.py` 当前使用 `HTTPServer`。早期使用 `ThreadingHTTPServer` 时，Playwright 同步 API 在 Windows 请求子线程中出现过 `[Errno 22] Invalid argument`。采集本身已经在后台线程运行，HTTP 请求保持顺序处理是有意选择。

### 测试缺口

- 没有服务重启后续跑的端到端测试；
- 没有历史报告失效测试；
- 没有 30 页以上的修复后压力测试；
- UI 冒烟测试会依赖本机 Edge 登录态，不是完全离线。

## 18. 2026-08-29 新发现：类目列表失败与极端环比解析失败

详细记录见：[故障记录-类目列表接口失败与极端环比解析失败-20260829.md](故障记录-类目列表接口失败与极端环比解析失败-20260829.md)。本节前两小节保留原始故障结论，18.3 记录后续真实响应、修复和验收结果。

### 18.1 特定二级类目列表接口失败

复现现场：`粮油干货/方便速食 / 干货`，`first_cid=1000009090`、`second_cid=1000009124`，当前失败检查点为 `data/checkpoints/api-1000009090-1000009124-2500000.json`。2026-08-29 08:07 和 08:08 两次任务都在第 1 页列表解析前失败，页检查点、成功商品和失败商品均为 0。

当前 `collect.py` 的 `fetch_list()` 对所有选择范围都只发送一个类目对象；选择二级父类目时只发送 `first_cid + second_cid`，没有将其子类目展开，也没有验证该父节点是否支持直接列表查询。对比历史现场：同一父类目下的三级 `果类干货`（`third_cid=1000009877`）曾返回 `code=0` 并成功采集。这说明问题集中在二级父类目范围的参数语义或平台业务限制，而不是通用认证、网络或整个列表接口不可用。

当前还不能确定平台返回的精确拒绝原因，因为失败列表响应没有保存；代码只从顶层 `message` 和 `base_resp.status_message` 提取错误，缺失时显示通用文本“列表接口返回失败”。修复前必须先保存脱敏请求体和失败响应，与同父类目的三级成功响应对照。

### 18.2 极端增长/下降商品被判指标失败

2026-08-29 的 `传统滋补 / 药食同源食品` 小样本中，`免洗有机本草银耳`（`clue_id=71462589`）和 `新疆带籽沙棘原浆`（`clue_id=78173274`）各重试 3 次后失败，原因均为“环比值缺失、单位异常或无法反推昨日成交”。截图显示前者在平台真实页面有 `¥10万-¥25万` 和 `▲999.99%+` 的有效展示。

该错误来自本地 `classify_indicator()`，不是 HTTP/认证错误。当前代码先拒绝 `pay_amount_hb <= -1` 或 `abs(pay_amount_hb) > 1000`，再判断 `999.99%+`；因此极端上涨、极端下降或特殊展示值可能在分类前被误判。失败记录还没有保存 `raw_indicator`，无法从现有检查点确认目标商品的精确原始环比字段形态。

后续修复必须分别覆盖：普通上涨/下跌、`999.99%+` 超大数值、平台特殊展示值、极端下降以及无法反推昨日成交的情况；“不能反推昨日”不应自动等同于“不能识别增长分类”。在补充原始指标证据和边界测试前，不要仅通过降低并发或增加等待处理该问题。
