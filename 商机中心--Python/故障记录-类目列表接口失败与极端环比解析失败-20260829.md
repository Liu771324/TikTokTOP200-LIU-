# 故障记录：特定类目列表接口失败与极端环比指标解析失败

> 记录日期：2026-08-29
>
> 调查范围：本地代码、当前检查点、当前报告和用户提供的三张截图
>
> 当前状态：已完成真实响应核验、代码修复、失败商品重试、完整离线单测和 UI 冒烟；特定二级类目的旧失败响应无法追溯，已补充脱敏诊断等待再次发生时留证

## 结论摘要

本次包含两个不同层级的问题，不能合并为一个“平台不稳定”问题：

1. `粮油干货/方便速食 / 干货` 的失败发生在第 1 页列表响应解析阶段。当前代码把选择的二级父类目直接组装为一个 `second_cid` 请求，没有实现“父类目展开为子类目”的处理。相同父类目下的三级类目 `果类干货` 曾成功采集，因此可以确认认证、HTTP 通道和列表解析主流程并非普遍失效；但由于失败响应没有落盘，平台对该二级范围返回的精确业务原因目前还不能确定。

2. `免洗有机本草银耳` 等商品的失败发生在指标响应已经进入本地分类之后。代码把极端环比统一送入“昨日成交反推”校验，并用 `pay_amount_hb <= -1` 或 `abs(pay_amount_hb) > 1000` 判为失败；同时失败记录不保存 `raw_indicator`。这会把平台真实展示的 `999.99%+` 或极端下降结果丢到失败记录，无法生成图三所示的业务结果。

## 一、问题一：特定二级类目列表接口返回失败

### 1. 现场证据

当前检查点：

```text
data/checkpoints/api-1000009090-1000009124-2500000.json
```

任务元数据：

| 字段 | 值 |
|---|---|
| 类目 | 粮油干货/方便速食 / 干货 |
| first_cid | 1000009090 |
| second_cid | 1000009124 |
| third_cid | 空 |
| 最低成交金额 | 2,500,000 |
| 当前页 / 下一页 | 0 / 1 |
| 成功 / 失败商品 | 0 / 0 |
| page_checkpoints | 0 |
| last_error | 列表接口返回失败 |

该任务在 2026-08-29 08:07 和 08:08 各重试过一次，分别对应：

- `business-20260829080717-a9bc4516`；
- `business-20260829080758-8898bed8`。

两次都在第 1 页、列表解析前失败，说明不是某个商品字段或分页边界导致。

### 2. 调用链和直接触发点

前端在 `public/index.html` 中把选中的一级、二级、三级 ID 原样提交。后端 `collect.py` 的 `ApiClient.fetch_list()` 只构造一个类目对象：

```json
{
  "first_cid": 1000009090,
  "second_cid": 1000009124
}
```

它不会把二级父节点下的三级类目展开为多个类目对象，也不会根据官方类目树判断该父节点是否可以直接作为列表查询范围。

响应进入 `parse_list_response()` 后，代码首先检查顶层 `code`。当 `code` 不为 `0` 或 `null` 时，抛出平台错误；只有顶层 `message` 或 `base_resp.status_message` 能识别时才展示原文，否则退回通用文本“列表接口返回失败”。网页后台随后把该异常标记为任务失败并生成部分报告。

因此，截图一中的通用错误不是“没有商品”，而是列表 API 的业务响应没有通过当前解析器的成功条件。

### 3. 根因判断

已确认的根因链：

```text
选择二级父类目“干货”
  → 代码只发送 second_cid=1000009124
  → 没有展开子类目或验证该父节点的 API 查询语义
  → 平台返回非成功列表业务响应
  → 原始失败响应未保存，错误字段又未完整提取
  → UI 只能显示“列表接口返回失败”
```

差异证据：同一父类目下，历史检查点

```text
data/archives/test-artifacts-before-retest-20260828/checkpoints/api-1000009090-1000009124-1000009877-500000.json
```

对应三级类目 `果类干货`，请求成功返回 `code=0`，第 1 页 18 条、其中 15 条达标；而当前失败任务没有任何页检查点。这说明问题集中在“二级父类目范围的请求语义/参数组合”，不是该一级类目、认证态或整个列表 API 都不可用。

### 4. 尚不能确认的部分

目前不能把平台的精确拒绝原因写成“必然是参数错误”或“必然需要三级 ID”，因为失败任务没有保存列表接口原始 JSON，也没有保存最终请求体和响应头。当前只能确认：

- 代码确实发送了二级 ID、没有第三 ID；
- 该范围连续两次在第 1 页失败；
- 同父类目的一个三级范围曾成功；
- 失败文本可能是代码的兜底文本，不等于平台原文。

要关闭这一证据缺口，后续必须在不记录 Cookie 的前提下保存一次脱敏的请求体、HTTP 状态、顶层响应键、`code`、`message`、`base_resp` 和 `data` 形状，并与同父类目的三级成功请求做对比。

## 二、问题二：极端增长或下降商品被判为指标失败

### 1. 现场证据

当前检查点：

```text
data/checkpoints/api-1000002718-1000002731-750000.json
```

该任务已经完成 3 页小样本，52 条成功、2 条失败。失败商品为：

| 商品 | clue_id | 页码 | 近30天成交 | 尝试次数 | 失败原因 |
|---|---:|---:|---:|---:|---|
| 免洗有机本草银耳 | 71462589 | 1 | 7,565,525.45 | 3 | 环比值缺失、单位异常或无法反推昨日成交 |
| 新疆带籽沙棘原浆 | 78173274 | 2 | 4,735,477.87 | 3 | 环比值缺失、单位异常或无法反推昨日成交 |

截图二中的错误文本与 `classify_indicator()` 中的固定错误文本完全一致。截图三又显示 `免洗有机本草银耳` 在平台页面中有真实的近 1 天成交档位 `¥10万-¥25万`，以及 `▲999.99%+` 的成交增长展示。因此该商品并非列表缺失，也不是业务上没有指标，而是本地解析/分类没有接受该极端值。

类似情况此前还出现在 `开口黑南瓜子`，报告中同样记录为“环比值缺失、单位异常或无法反推昨日”。这说明问题具有重复性。

### 2. 直接触发点

指标处理顺序如下：

1. `parse_indicator_response()` 校验响应为 JSON，并校验返回的 `clue_id`；
2. `classify_indicator()` 读取 `pay_amount`、`pay_amount_range` 和 `pay_amount_hb`；
3. 代码先执行：

```python
if not math.isfinite(hb) or hb <= -1 or abs(hb) > 1000:
    raise CollectorError("环比值缺失、单位异常或无法反推昨日成交")
```

4. 只有通过该检查后，代码才会判断 `hb >= 9.9999` 并分类为 `999.99%+`；
5. 在此之前或之后还会按 `今日成交 ÷ (1 + 环比)` 反推昨日成交。

该错误文本来自本地 `classify_indicator()`，不是 `ApiClient._post()` 的 HTTP/认证错误文本。因此截图二至少能确认：指标请求已经走到本地分类校验，失败发生在极端环比的解释规则上。

### 3. 根因判断

这是“展示口径”和“内部数值校验”没有分层造成的边界错误：

- 平台的 `999.99%+` 是展示分类，实际原始 `pay_amount_hb` 可能远大于普通增长值，也可能使用特殊字符串/哨兵值；
- 当前代码却用固定上限 `1000` 把过大的数值先判为异常；
- 对极端下降，`hb <= -1` 会使昨日反推公式失去有效意义，代码直接失败，没有保留平台的极端下降业务状态；
- 对无法转成浮点数的特殊展示值，代码同样归入“环比值缺失/单位异常”；
- 代码把“能否反推昨日成交”作为“能否识别增长分类”的前置条件，导致即使今日成交和增长方向已可读，也不能输出增长分类。

已有成功记录证明当前逻辑只能覆盖部分极端增长：例如原始环比 `13.7104`、`213.7102`、`459.3272`、`821.5602` 已被分类为 `999.99%+`；离线自测只覆盖到 `10.5`，没有覆盖大于 `1000`、小于等于 `-1` 或特殊字符串值的边界。

### 4. 额外的可观测性缺陷

失败记录只保存 `raw_list`，不保存已经请求到但分类失败的 `raw_indicator`。因此当前检查点无法回答 `免洗有机本草银耳` 的精确原始 `pay_amount_hb` 是：

- 数值大于 `1000`；
- 非数值的 `999.99%+` 哨兵/展示字符串；
- 小于等于 `-1` 的极端下降值；
- 或其他单位格式。

这也是本次调查对具体数值只能做范围判断、不能伪造精确值的原因。

## 三、当前影响

- `干货`二级范围在第 1 页即失败，不能进入列表采集和阈值筛选。
- 极端增长/下降商品在重试 3 次后进入失败记录，真实平台结果没有进入“全部数据”和“成交增长”。
- 失败商品的指标原始响应没有留存，后续只能依赖页面截图或重新采集才能确认原始字段。
- 报告中的“失败数量”会增加，分类统计与平台实际可展示结果不一致。

## 四、调查边界和后续验证顺序

本次没有启动采集、没有调用平台 API、没有修改业务代码；只读取了本地代码、检查点、报告和用户截图。

后续若进入修复阶段，验证顺序应保持为：

1. 先记录一次脱敏的二级失败列表响应，并与同父类目三级成功响应对比，确认平台真正要求的类目参数语义。
2. 在保存指标失败记录时保留脱敏 `raw_indicator` 和原始字段类型，确认极端商品的 `pay_amount_hb` 实际形态。
3. 再分别设计极端上涨、极端下降、特殊展示值和普通值的测试，不把平台业务展示值直接等同于接口异常。

在这两个证据缺口关闭前，不应把降低并发、增加等待或重复点击重试当作根因修复。

## 五、2026-08-29 修复与验证结果

### 1. 特定二级类目：不实施未经证实的子类目展开

使用同一 Edge 登录态、同一请求结构进行低频只读对照：

- 二级范围 first_cid=1000009090、second_cid=1000009124，第 1 页返回 code=0、18 条；
- 三级范围再加 third_cid=1000009877，第 1 页同样返回 code=0、18 条。

这证明二级父类目当前支持直接查询，因此没有把“展开全部三级类目”写成修复。旧任务当时的精确业务失败原因仍无法从已有文件恢复。

已补充以下可观测性：

- 列表业务失败保存脱敏请求体、HTTP 状态、白名单响应头、顶层键、code、message、base_resp 和 data 形状；
- 响应头只保留 content-type、content-length 和请求追踪类字段，不保存 Set-Cookie；
- 诊断写入检查点的 last_list_failure，下次同类失败可直接确认平台原文和响应结构；
- 平台错误文本兼容 message、msg、base_resp.status_message、base_resp.status_msg 等常见位置。

### 2. 极端环比：真实根因已确认并修复

重新只读请求两个失败商品，原始字段均为浮点数：

| 商品 | clue_id | pay_amount_hb | 修复后分类 |
|---|---:|---:|---|
| 免洗有机本草银耳 | 71462589 | 1385.9357 | 999.99%+ |
| 新疆带籽沙棘原浆 | 78173274 | 1225.7599 | 999.99%+ |

两者都被旧代码的 abs(hb) > 1000 上限误杀。修复后：

- 不再对有限的正数环比设置 1000 上限；
- 数值大于等于 9.9999 时分类为 999.99%+，仍可反推时保留昨日成交档位；
- 平台直接返回 ▲999.99%+ 等特殊展示值时可分类，但昨日成交显示“-”，不伪造精确值；
- hb <= -1 的极端下降可识别为“下跌/极端下降”，昨日成交显示“-”；
- 真正无法解析的指标仍进入失败记录，并保留最后一次 raw_indicator 及字段类型。
